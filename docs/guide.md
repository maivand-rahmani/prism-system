# Гайд для человека

Практическое руководство по репозиторию **Maivand Design Systems**. Написано
простым языком: что это, как запустить, как создать дизайн-систему, как
подключить её к продукту и как выпускать версии. Технические контракты целиком
здесь не дублируются — ссылки на них в конце.

## 1. Что это за проект и чем он не является

**Это** монорепозиторий, где отдельно живут дизайн-системы (внешний вид) и
инструменты, которые помогают их создавать, проверять и подключать к продуктам.

**Это не** приложение и не продукт: здесь нет бизнес-логики, данных, роутинга
или экранов конкретного продукта. Продукт — отдельный репозиторий, который
устанавливает готовый npm-пакет дизайн-системы.

**Это не** AI-платформа: в репозитории нет LLM, агентов и API. Внешний
coding-агент просто читает файлы-инструкции (`AGENTS.md`, `skills/`) и запускает
обычные команды `pnpm ds:*`.

Материалы завершённых этапов разработки лежат в
[`docs/archive/`](archive/README.md). Это архив, а не текущие правила: актуальная
документация — этот гайд и [текущая спецификация](v4/README.md).

## 2. Архитектура и направление зависимостей

Представьте конструктор:

- `@prism-system/ui-core` — **фундамент и правила**: какие компоненты обязаны
  существовать и какие у них типы. Единственный текущий контракт — **версия 4**:
  29 обязательных компонентов и 17 дополнительных контрактов. Без цветов и стилей.
- `@prism-system/ui-system-a` / `@prism-system/ui-system-b` — **наборы деталей
  внешнего вида**: смысловые токены, CSS, варианты, состояния, анимации. Каждая
  система реализует все 29 обязательных компонентов и только те дополнительные,
  которые объявила в манифесте.
- `apps/showcase` — **витрина**: живой каталог зарегистрированных систем,
  Foundations и компонентов по маршруту `/showcase/<id>`.
- `apps/reference-app` — **тестовая комната**: один и тот же интерфейс собирается
  на System A и на System B.
- Продукт — **покупатель**: берёт готовый набор и собирает свои экраны.

Направление зависимостей всегда одно:

```text
apps/*  ──────────►  @prism-system/ui-system-*  ──────────►  @prism-system/ui-core
```

Правила простые:

- `core` не зависит ни от дизайн-систем, ни от приложений;
- дизайн-система не зависит от другой дизайн-системы;
- приложения только компонуют и не переопределяют внешний вид.

## 3. Кто что делает: человек и внешний coding-агент

| Кто                       | Что делает                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------------- |
| **Человек**               | Принимает визуальные решения, подтверждает Design Brief, ревьюит результат, решает про релиз.      |
| **Внешний агент**         | Читает `AGENTS.md` и `skills/`, реализует компоненты, запускает `ds:*` команды, готовит Changeset. |
| **Репозиторий (скрипты)** | Даёт детерминированные команды: генерация, проверка, манифест, синхронизация версий, подключение.  |

Что агент использует автоматически:

- `AGENTS.md` — правила репозитория;
- `skills/create-design-system/SKILL.md`, `skills/use-design-system/SKILL.md`,
  `skills/modify-design-system/SKILL.md` — пошаговые сценарии;
- `design-system.json` — сгенерированный манифест пакета (компоненты, варианты,
  размеры, составные части, имена токенов, правила использования), доступный
  потребителю по публичному пути `./manifest`;
- `README.md` и `AGENTS.md` пакета — краткий маршрут чтения и правила;
- `scripts/*` — команды `ds:*`.

## 4. Первый локальный запуск

```bash
pnpm install
pnpm build
pnpm typecheck
pnpm lint
```

Если меняли зависимости, сначала `pnpm install`, потом остальные команды.

## 5. Как открыть Showcase и Reference App

Приложения — это Next.js. Запускайте их по отдельности:

```bash
# витрина компонентов
pnpm --filter @prism-system/showcase dev

# тестовая сборка интерфейса
pnpm --filter @prism-system/reference-app dev
```

- Showcase: откройте в браузере `/showcase/<id>` (например, `/showcase/system-a`) —
  это живой каталог выбранной системы: Foundations строятся из её реальных токенов,
  а компоненты берутся из её публичного API.
- Reference App: откройте корневую страницу — там тот же интерфейс, но можно
  переключать дизайн-систему.

`pnpm dev` запускает все dev-цели через Turborepo сразу; для повседневной работы
удобнее запускать приложения по одному.

## 6. Контракт: 29 обязательных и 17 дополнительных

Текущий контракт один — **версия 4** (в runtime — числовое
`contractVersion: 4`). Обе системы реализуют **29 обязательных компонентов**:

```text
Button, Input, Textarea, Card, Badge, Checkbox, RadioGroup, Switch, Select,
Tabs, Dialog, DropdownMenu, Tooltip, Separator, Heading, Text, Link, Container,
Stack, FormField, Center, Cluster, Sidebar, AspectRatio, Combobox, DatePicker,
NumberField, Slider, FileUpload
```

Дополнительно каждая система может реализовать любой из **17 дополнительных
контрактов**:

```text
Grid, Section, Fieldset, Alert, Progress, Skeleton, Toast, Accordion, Avatar,
Breadcrumbs, Pagination, Table, Metric, DescriptionList, Timeline, Meter,
EmptyState
```

Дополнительные компоненты — это реальные capabilities, а не заглушки. Если системы
нет в списке — значит, она его не предоставляет. Фактический набор:

| Система  | Дополнительные capabilities |
| -------- | --------------------------- |
| System A | `Grid`, `Fieldset`, `Alert`, `Progress`, `Accordion`, `Pagination`, `Table`, `Metric`, `DescriptionList`, `Meter`, `Timeline` |
| System B | `Section`, `Alert`, `Skeleton`, `Toast`, `Avatar`, `Breadcrumbs`, `Metric`, `Timeline`, `EmptyState` |

Разница между A и B — во внешнем виде и в наборе дополнительных компонентов.
Именно поэтому Reference App может переключать систему, не переписывая интерфейс.

Источник истины по составу, вариантам, размерам и составным частям — манифест
`design-system.json` (`schemaVersion: 4`, `contractVersion: 4`; публичный путь
`./manifest`). Доступность компонента в конкретной системе определяет только
наличие ключа в `components` манифеста; `capabilities.categories` (`composition`,
`forms`, `data-display`) — канонический перечень принадлежности категориям, общий
для всех систем, а не второй список доступности, и категории охватывают не все
контракты. Package-owned descriptor `design-system.source.json` остаётся
`schemaVersion: 3`, служит только входом генератора и не содержит блок
`capabilities` — его туда не добавляют и не повторяют. Форма манифеста одна:
читатели `schemaVersion: 3` обновляются вместе с системой, потому что текущий
`prism-ds` требует schema 4 и отклоняет schema 3. Посмотреть конкретную систему:

```bash
# документация и правила пакета
cat packages/system-a/README.md
cat packages/system-a/AGENTS.md

# фактический каталог из манифеста
node -e "const m=require('./packages/system-a/design-system.json'); console.log(Object.keys(m.components))"

# структура: токены, стили, компоненты
ls packages/system-a/src
```

## 7. Создание новой дизайн-системы

Обычно этим занимается внешний агент по скиллу
`skills/create-design-system/SKILL.md`. Коротко шаги такие:

1. **Интервью** с человеком: продукт, аудитория, визуальное направление,
   foundations (акцент, температура цвета, контраст, типографика, радиус,
   поверхности, границы, тени, анимация), компоненты.
2. **Design Brief** — человек подтверждает решения. Бриф сохраняется в
   `design-briefs/<id>.json` и проверяется по схеме
   `skills/create-design-system/design-brief.schema.json`.
3. **Генерация пакета** из шаблона:

   ```bash
   # сначала предпросмотр
   pnpm ds:create <id> --name "<Название>" --brief design-briefs/<id>.json --dry-run
   # затем создание
   pnpm ds:create <id> --name "<Название>" --brief design-briefs/<id>.json
   ```

4. **Реализация внешнего вида** — только внутри `packages/<id>` (токены, стили,
   компоненты). Новый пакет уже содержит 29 обязательных компонентов; выбранные
   дополнительные добавляются по той же структуре и объявляются в
   `design-system.source.json`.
5. **Регистрация и синхронизация приложений** (обычно уже сделана генератором;
   повторить можно так):

   ```bash
   pnpm ds:register <id>
   ```

6. **Проверка:**

   ```bash
   pnpm ds:check <id>
   ```

7. **Подготовка релиза** (без публикации):

   ```bash
   pnpm ds:release <id> --approved
   ```

`ds:create` сам пишет `README.md`, `AGENTS.md`, `LICENSE`, `package.json`,
`design-brief.json`, `design-system.json` и 29 обязательных компонентов. Руками
структуру пакета не создавайте: обязательный набор фиксирован, а дополнительные
компоненты добавляются только осознанно.

## 8. Использование пакета в реальном продукте

Продукт — отдельный репозиторий. Ему нужны два пакета из npm: сама дизайн-система и
потребительский инструмент [`@prism-system/tools`](../packages/tools/README.md) с
исполняемым файлом `prism-ds`:

```bash
# внутри репозитория продукта
npm install @prism-system/ui-system-a
npm install --save-dev @prism-system/tools
```

Дальше каталог, установка, настройка и проверка выполняются из корня продукта и **не
требуют доступа к репозиторию дизайн-систем**:

```bash
# найти и изучить опубликованные системы (сеть, только чтение)
npx prism-ds search "calm editorial"
npx prism-ds info @prism-system/ui-system-a --json

# явно установить и подключить (меняют зависимости продукта)
npx prism-ds use @prism-system/ui-system-a --cwd . --check-usage

# обновление до точной версии: сравнит манифесты и покажет изменения
npx prism-ds upgrade @prism-system/ui-system-a <exact-version> --cwd . --dry-run

# каталог установленной системы (офлайн, только её манифест)
npx prism-ds components Button --cwd .
npx prism-ds tokens color --cwd .

# обычный CSS и мост к Tailwind v4 (офлайн; меняется только указанный файл)
npx prism-ds setup-tailwind --cwd . --css app/globals.css --dry-run

# отчёт о состоянии продукта и офлайн-диагностика
npx prism-ds check --cwd . --css app/globals.css
npx prism-ds connect @prism-system/ui-system-a --cwd .
npx prism-ds check-usage --cwd .
npx prism-ds doctor --cwd .
```

Границы команд:

- `search` и `info` — **явная сеть, только чтение** (реестр npm; `--registry` для
  другого реестра). `info` проверяет точную версию, `contractVersion: 4`,
  `exports["./manifest"]`, SRI-целостность и манифест `design-system.json`.
- `install`, `use` и `upgrade` — **единственные команды, которые меняют зависимости
  продукта**. Они сначала проверяют точную версию в реестре, определяют npm/pnpm
  (без молчаливого выбора npm), запускают фиксированную команду с `--ignore-scripts`
  и без пользовательских аргументов, затем проверяют установленный пакет. `use`
  после установки вызывает `connect` (и при `--check-usage` — проверку
  использования), `upgrade` перед обновлением сравнивает манифесты и сообщает
  об исчезнувших/добавленных компонентах и токенах. `--dry-run` доступен для всех
  трёх команд.
- `connect`, `components`, `tokens`, `check`, `check-usage`, `doctor` и
  `setup-tailwind` — **офлайн**. `connect` пишет только consumer-конфиг и
  инструкции; `setup-tailwind` меняет только явно названный CSS-файл; каталоги,
  отчёты и диагностика ничего не пишут. Ни одна из них не устанавливает пакеты, не
  меняет зависимости и не читает этот репозиторий.

`prism-ds connect` — **только настройка**. Он:

- создаёт `<product>/.design-system/config.json` (пакет, точная версия, путь к
  манифесту `./manifest`, режим `strict`);
- создаёт `<product>/.design-system/AGENTS.md` с инструкциями для агента;
- аккуратно добавляет управляемый блок в `<product>/AGENTS.md`, сохраняя ваш
  текст.

Чего `connect` **не делает**: не устанавливает пакеты, не делает сетевых вызовов, не
меняет `package.json` и зависимости продукта, не копирует исходники компонентов и не
читает этот репозиторий.

`prism-ds doctor` — это диагностика только для чтения: containment, найденный пакет и
его личность, установленная версия, публичный манифест `./manifest`, совпадение версий
и состояние конфига. `prism-ds check` — агрегированный отчёт того же уровня:
конфиг, публичные CSS/bridge-экспорты, prerequisites Tailwind v4, строгое
использование и доступность обязательных/дополнительных компонентов. Порядок
импортов CSS он проверяет только при явном `--css <file>`.

Точная версия важна: версия в конфиге, версия установленного `package.json` и
версия в манифесте `design-system.json` должны совпадать. Если они разошлись,
`connect` завершится ошибкой.

Проверка строгого использования в продукте:

```bash
npx prism-ds check-usage --cwd .
```

Инструмент ищет «обходы» дизайн-системы: произвольные цвета/радиусы/тени в
классах, визуальные inline-стили, локальные дубликаты компонентов. В режиме
`strict` находки — это ошибки (ненулевой код выхода), в нестрогом режиме —
предупреждения.

В этом репозитории те же действия доступны как обёртки мейнтейнера:
`pnpm ds:connect --cwd <root>` и `pnpm ds:check-usage --cwd <root>`. Они используют
ровно ту же реализацию, что и опубликованный `prism-ds`, и нужны для локальной
разработки и проверок. Остальные команды `ds:*` (`ds:create`, `ds:check`,
`ds:manifest`, `ds:release`, `ds:check-tools`, `ds:check-docs`, `ds:check-all`) —
инструменты мейнтейнера и не публикуются.

### Обычный CSS и Tailwind v4

Потребителю без Tailwind достаточно один раз импортировать CSS пакета:

```tsx
import "@prism-system/ui-system-a/styles.css";
```

Продукт с Tailwind v4 подключает мост пакета. Порядок импортов один и тот же:
сначала `tailwindcss`, затем `<package>/tailwind.css`, затем `<package>/styles.css`:

```css
@import "tailwindcss";
@import "@prism-system/ui-system-a/tailwind.css";
@import "@prism-system/ui-system-a/styles.css";
```

Мост (`@theme inline`) отдаёт смысловые utility-классы вроде `bg-prism-surface`
для того же набора токенов, которым оформлены компоненты. Брейкпоинты статичны,
одна сборка подключает мост одной выбранной системы, и обычное потребление без
Tailwind по-прежнему работает. Повторный `prism-ds setup-tailwind` идемпотентен:
он не меняет файл, если импорты уже стоят правильно.

Готовые примеры контентной страницы, доступной формы и страницы с данными — в
[рецептах потребителя](v4/recipes.md).

## 9. Стилизация: продукт vs дизайн-система

| Отвечает дизайн-система                        | Отвечает продукт                    |
| ---------------------------------------------- | ----------------------------------- |
| цвета, типографика, отступы, радиусы           | бизнес-логика, данные, роутинг      |
| границы, поверхности, тени                     | состояние фич, композиция страниц   |
| состояния и варианты компонентов               | раскладка, размещение, адаптивность |
| анимация, переиспользуемые визуальные паттерны | продуктовые и фичевые компоненты    |

Хорошо — используем готовый API:

```tsx
import { Button, Card, Input } from "@prism-system/ui-system-a";
import "@prism-system/ui-system-a/styles.css";

export function SaveCard() {
  return (
    <Card>
      <Card.Header>
        <Card.Title>Сохранить изменения</Card.Title>
      </Card.Header>
      <Card.Content>
        <Input label="Название" />
        <Button variant="primary">Сохранить</Button>
      </Card.Content>
    </Card>
  );
}
```

Плохо — переопределяем внешний вид:

```tsx
<Button className="rounded-full bg-[#356AFF] shadow-[0_8px_30px_rgba(0,0,0,0.2)]">Сохранить</Button>
```

Раскладка в продукте разрешена: `grid`, `flex`, `gap`, отступы, размеры,
позиционирование, адаптивность. Запрещено менять визуальный язык.

## 10. Новый переиспользуемый компонент

Если готового компонента не хватает, порядок решений такой:

```text
Нужен новый UI
   ↓
Есть ли он уже в дизайн-системе (манифест и публичный API)?
   ↓ да → используем
   ↓ нет
Это бизнес-специфично?
   ↓ да → оставляем в продукте, собирая из примитивов дизайн-системы
   ↓ нет
Это переиспользуемый визуальный паттерн?
   ↓ да → возвращаем в репозиторий дизайн-системы
```

Если нужен один из дополнительных контрактов (`Table`, `Toast`, `Accordion`
и т. п.), которого у системы пока нет, — это осознанное расширение системы:
компонент реализуется полностью и объявляется в descriptor и манифесте. Пустые
заглушки запрещены.

Для возврата используется скилл `skills/modify-design-system/SKILL.md`:
сначала читаем Design Brief, токены, `AGENTS.md` и существующие компоненты,
потом меняем только `packages/<id>`, обновляем манифест и документацию,
прогоняем `ds:check`, добавляем Changeset и останавливаемся перед ручным
релизом.

## 11. Релиз и версионирование простыми словами

Версионирование и публикация — **ручные шаги, управляемые человеком** через
Changesets.

```text
Изменение в коде
   ↓
pnpm changeset                # человек описывает изменение
   ↓
CI готовит version PR         # изменения версий + синхронизация версий
   ↓
ревью и merge PR              # человек одобряет
   ↓
workflow публикации           # защищённое окружение, OIDC
   ↓
пакет в npm
```

Что **никогда** не происходит автоматически:

- локальные команды `ds:release`, `ds:check`, `ds:check-tools`, `ds:check-docs`
  и `ds:check-all` не публикуют и не версионируют пакеты;
- `ds:release <id> --approved` только готовит релиз: валидирует, синхронизирует
  версии, собирает, упаковывает и создаёт/переиспользует Changeset;
- `pnpm version-packages-and-sync` — это CI-команда (её запускает workflow перед
  созданием version PR), а не повседневная команда.

Версия установленного пакета, runtime `DesignSystem.version`, сгенерированный
`design-system.json` и запись в `config/design-systems.json` должны совпадать;
синхронизирует их `pnpm ds:sync-versions` (проверка — `--check`). Историю
подготовки версий и миграцию потребителя с прежнего контракта смотрите в
[архиве](archive/README.md).

## 12. Шпаргалка по командам

**Человек использует часто:**

| Команда                                         | Зачем                              |
| ----------------------------------------------- | ---------------------------------- |
| `pnpm install`                                  | Поставить зависимости              |
| `pnpm build`                                    | Собрать всё                        |
| `pnpm typecheck`                                | Проверить типы                     |
| `pnpm lint`                                     | Проверить код линтером             |
| `pnpm format`                                   | Отформатировать                    |
| `pnpm --filter @prism-system/showcase dev`      | Открыть витрину                    |
| `pnpm --filter @prism-system/reference-app dev` | Открыть тестовую сборку            |
| `pnpm ds:check <id>`                            | Проверить дизайн-систему           |
| `pnpm ds:release <id> --approved`               | Подготовить релиз (без публикации) |
| `pnpm changeset`                                | Описать изменение для релиза       |

**В основном для агента и CI:**

| Команда                                | Зачем                                             |
| -------------------------------------- | ------------------------------------------------- |
| `pnpm ds:create <id>`                  | Создать новую дизайн-систему                      |
| `pnpm ds:register <id>`                | Зарегистрировать и синхронизировать систему       |
| `pnpm ds:manifest <id> [--write]`      | Проверить/пересобрать `design-system.json`        |
| `pnpm ds:sync-versions [id] [--check]` | Синхронизировать версии runtime/манифест/реестр   |
| `pnpm ds:check-tools`                  | Проверка `prism-ds` и манифестов на packed-артефактах |
| `pnpm ds:check-docs`                   | Проверка активной документации и локальных ссылок |
| `pnpm ds:check-all`                    | Полный приёмочный прогон                          |
| `pnpm ds:connect --cwd <root>`         | Настроить продукт-потребитель                     |
| `pnpm ds:check-usage --cwd <root>`     | Строгая проверка использования в продукте         |
| `pnpm version-packages`                | CI: применить Changesets                          |
| `pnpm version-packages-and-sync`       | CI: версии + синхронизация                        |
| `pnpm release`                         | CI: проверка синхронизации, сборка, публикация    |

**В продукте-потребителе (пакет `@prism-system/tools`, из npm):**

| Команда                                                   | Зачем                                            |
| --------------------------------------------------------- | ------------------------------------------------ |
| `npx prism-ds search [query...]`                          | Найти системы в npm (сеть, только чтение)        |
| `npx prism-ds info <package-or-id> [version]`             | Изучить манифест системы (сеть, чтение)          |
| `npx prism-ds install <package-or-id> --cwd .`            | Явно установить систему (меняет зависимости)     |
| `npx prism-ds use <package-or-id> --cwd .`                | Установить и подключить одной командой           |
| `npx prism-ds upgrade <package-or-id> <version> --cwd .`  | Обновить до точной версии с диффом манифеста     |
| `npx prism-ds components [name] --cwd .`                  | Каталог компонентов установленной системы (офлайн) |
| `npx prism-ds tokens [group] --cwd .`                     | Имена токенов и их CSS/Tailwind-имена (офлайн)   |
| `npx prism-ds check --cwd . [--css <file>]`               | Сводный отчёт о продукте (офлайн)                |
| `npx prism-ds setup-tailwind --cwd . --css <file>`        | Подключить мост Tailwind v4 в указанный CSS      |
| `npx prism-ds connect [package] --cwd .`                  | Настроить продукт-потребитель (офлайн)           |
| `npx prism-ds check-usage --cwd .`                        | Строгая проверка использования (офлайн)          |
| `npx prism-ds doctor [package] --cwd .`                   | Диагностика только для чтения (офлайн)           |

## 13. Частые проблемы

| Симптом                                          | Что это значит и что делать                                                                                                                         |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| «Пакет не установлен» при `prism-ds connect`     | В продукте нет `@prism-system/ui-*`. Установите его (`npm install @prism-system/ui-system-a`) и повторите.                                          |
| Ошибка про `--cwd`                               | Команде нужен явный корень продукта: `--cwd ../my-product`. Без него команда не угадывает путь.                                                     |
| «Версии не совпадают»                            | Конфиг, установленный пакет и манифест разошлись. В репозитории дизайн-систем запустите `pnpm ds:sync-versions`; в продукте повторите `prism-ds connect`. |
| Находки `ds:check-usage`                         | В продукте есть обходы дизайн-системы. Замените произвольные цвета/радиусы/тени и inline-стили на API компонентов.                                  |
| `ds:check-tools` / `ds:check-all` падают         | Сначала `pnpm install && pnpm build` — проверкам нужны собранные пакеты.                                                                            |
| Tailwind-классы не работают                      | Проверьте порядок импортов: `tailwindcss` → `<package>/tailwind.css` → `<package>/styles.css`, и что подключён мост именно выбранной системы.        |
| Компонент из манифеста не найден                 | Дополнительные компоненты есть только у систем, которые их объявили: сверьтесь с `prism-ds components <Name>` и манифестом.                           |
| Не знаю, как пользоваться пакетом                | Смотрите `packages/<id>/README.md` и `packages/<id>/AGENTS.md`, манифест `<package>/manifest` и каталог `prism-ds components`.                        |
| Компонент выглядит не так                        | Правим `packages/<id>`, а не приложение и не продукт.                                                                                               |
