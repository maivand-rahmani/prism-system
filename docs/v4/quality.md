# Критерии качества V4

Этот документ задаёт обязательные проверки качества монорепозитория и границы их покрытия.

## Автоматические проверки

| Критерий | Проверка и граница гарантии |
| --- | --- |
| Сборка, lint, типы и форматирование workspace | CI: `pnpm build`, `pnpm lint`, `pnpm typecheck`, `pnpm format:check`. Форматирование исключает временные артефакты и сгенерированные token modules: последние проверяются по источнику V4 gate. |
| Node-тесты maintainer scripts, core, system и tools | `pnpm test` запускает поддерживаемые Node suites для scripts, core, систем и tools после сборки. Они проверяют утилиты, контракты и сценарии этих пакетов; сами по себе не подтверждают поведение каждого компонента в браузере. |
| Согласованность версий | `pnpm ds:sync-versions --check` подтверждает равенство версий package, runtime, манифестов и реестра без записи. |
| Активная документация | `pnpm ds:check-v4-docs` проверяет структуру, локальные ссылки и соответствие документации контрактам. Это не проверка качества каждого примера визуально. |
| Пакеты и lifecycle V4 | `pnpm ds:check-v4` — единый gate; он уже запускает `pnpm ds:check-v4-tools`, поэтому отдельно не учитывайте его повторно. Harness собирает и валидирует core, системы A/B, свежий пакет из шаблона и tools; пакует артефакты; проверяет public exports, манифесты, CSS и token exports; выполняет typecheck и runtime resolution импортов из изолированного consumer; проверяет обычный CSS и компилирует Tailwind v4 на точной версии для A/B. Также он проверяет сценарии V2 fixture и CLI из packed tools. |
| Изоляция lifecycle и release | `ds:check-v4` сверяет снимок отслеживаемых версий, конфигураций и манифестов до и после, проверяет, что lockfiles репозитория не меняются, и выполняет release-проверки на временных копиях. `ds:release` должен блокировать неполный или несогласованный пакет; harness проверяет fail-closed поведение, отсутствие изменений, упаковки и публикации при dry-run/ошибках. |

Общий verification workflow только проверяет код и артефакты. Изменение версий
проходит через Changesets и `pnpm version-packages-and-sync` в version PR.
Публикация выполняется отдельным [publish.yml](../../.github/workflows/publish.yml)
после merge version PR через environment `npm-release`; решение о выпуске
остаётся отдельным этапом review.

## Локальный запуск и CI

CI, release и проверка перед publish используют один workflow:
[verify.yml](../../.github/workflows/verify.yml).
Он устанавливает зависимости с frozen lockfile и выполняет все проверки из таблицы.
Ошибки блокируют продолжение workflow; нет `continue-on-error` или автоматического
повтора тестов. Браузер не устанавливается и не запускается в CI.

Для воспроизведения после `pnpm install --frozen-lockfile`:

```bash
pnpm format:check
pnpm build
pnpm lint
pnpm typecheck
pnpm test
pnpm ds:sync-versions --check
pnpm ds:check-v4-docs
pnpm ds:check-v4
```

`ds:check-v4` использует сеть для временной установки точных версий Tailwind в
каталог своего запуска. Недоступность registry проваливает
соответствующий шаг, а не считается успешной проверкой.

## Ручной review изменений интерфейса

Для изменённых компонентов и Showcase reviewer проверяет применимые пункты на живом сценарии обеих систем:

- управление клавиатурой, видимый и логичный focus;
- доступные имена и связи `label`, `aria-describedby`, ошибки и подсказки;
- состояния loading, empty, error и success там, где компонент или сценарий их поддерживает;
- компоновку на узком и широком экране;
- поведение при reduced motion и достаточную различимость контраста.

CI не доказывает браузерное поведение, соответствие WCAG или визуальную идентичность. Эти пункты требуют ручного review. Peer ranges в package metadata не доказывают совместимость каждой комбинации React 18/19 и зависимостей; новые или рискованные комбинации требуют отдельной проверки.

## Постоянные гарантии

- V2 остаётся замороженным контрактом из 14 компонентов. V4 требует ровно 20 компонентов и допускает только реализованные дополнительные компоненты, объявленные системой; пустые заглушки недопустимы.
- Пакет системы владеет токенами и визуальным оформлением. `tokens.source.json` — источник визуальных значений; `ui-core` остаётся неоформленной общей основой, приложения отвечают за композицию.
- Изменение несовместимого публичного API требует Changeset и документации миграции. Автоматические проверки помогают обнаружить рассогласование, а совместимость и понятность миграции оценивает review.
- Подготовка релиза проверяет и упаковывает артефакт, но не публикует его. Решение о публикации принимается отдельно.
