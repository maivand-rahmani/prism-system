# Prism V4 (репозиторий 0.4.0) — план разработки

Этот документ задаёт **пять последовательных фаз**. [Спецификация V4](README.md) описывает целевое поведение и структуру; здесь перечислены задачи, результаты и условия завершения для агента. Основа: [рекомендации из issue #9](https://github.com/maivand-rahmani/prism-system/issues/9) и реализованные [V1–V3](../archive/README.md).

## Цель и границы

После V4 агент может собрать целый интерфейс из компонентов и смысловых токенов Prism. Дизайн-система задаёт внешний вид и правила универсальных компонентов; продукт выбирает содержание, порядок блоков, маршруты, данные и действия. Компоненты систем оформляются обычным CSS на переменных. Обязательный Tailwind v4 bridge даёт продукту те же токены для композиции страниц.

Целевой каталог: **20 обязательных компонентов** в каждой системе и **12 дополнительных контрактов** в `ui-core`. Обязательные: `Button`, `Input`, `Textarea`, `Card`, `Badge`, `Checkbox`, `RadioGroup`, `Switch`, `Select`, `Tabs`, `Dialog`, `DropdownMenu`, `Tooltip`, `Separator`, `Heading`, `Text`, `Link`, `Container`, `Stack`, `FormField`. Дополнительные: `Grid`, `Section`, `Fieldset`, `Alert`, `Progress`, `Skeleton`, `Toast`, `Accordion`, `Avatar`, `Breadcrumbs`, `Pagination`, `Table`. Назначение каждого описано в [спецификации](README.md). Дополнительный компонент реализуется только по выбору системы и публикуется как capability; пустые заглушки запрещены. Имена, props, варианты и семантику всех 32 контрактов агент фиксирует в начале фазы 1 до разработки.

Работа идёт по фазам 1 → 5. После каждой фазы агент оставляет работающий репозиторий, описание сделанного, команды проверки и известные ограничения. Следующая фаза использует её результат; задачи будущих фаз не считаются завершёнными по одному только изменению типов или документации. Исторические `docs/archive/v1`, `v2`, `v3` не переписываются. Публикация пакетов остаётся отдельным явным действием человека.

**Задание агенту на каждую фазу:** «Прочитай корневой `AGENTS.md`, `docs/v4/README.md` и `docs/v4/PLAN.md`. Выполни фазу N целиком, включая её критерии готовности. Сохрани границы пакетов и существующие пользовательские изменения. Покажи изменённые файлы, результаты проверок и то, что осталось для следующей фазы». Фазы запускаются последовательно; перед фазой 5 должны быть завершены первые четыре.

## Версии V4

| Объект | До версии фазы 5 | Цель после фазы 5 | Почему |
| --- | --- | --- | --- |
| Приватный корень репозитория | `0.3.0` | `0.4.0` | Общая веха проекта V4; не версия npm-пакетов |
| `@prism-system/ui-core` | `1.0.0` | `2.0.0` | Новый публичный контракт 20 + 12 и новые типы системы |
| `@prism-system/ui-system-a`, `ui-system-b` | `1.1.0` | `2.0.0` | Переход публичного манифеста с V2 на V4, новая схема и capabilities |
| `@prism-system/tools` | `1.0.0` | `1.1.0` | Новые команды и чтение V4 при сохранении поведения команд V3 и поддержки V2 |

Правило [SemVer](https://semver.org/spec/v2.0.0.html): несовместимое изменение публичного API требует major, совместимое добавление — minor. Поэтому `@prism-system/ui-core` и системы получают major: меняется публичный контракт (20 обязательных + 12 дополнительных) и форма манифеста, а обратная совместимость **всех** публичных экспортов и старой формы манифеста не гарантируется. `@prism-system/tools` получает minor `1.0.0` → `1.1.0`: новые команды и чтение V4 добавляются, пока старые сценарии и их машинный вывод сохраняют совместимость. Если реализация нарушит границу совместимости, агент пересматривает целевой major до выпуска.

Версии подготовлены в фазе 5 через Changesets (`pnpm changeset`, затем `pnpm version-packages-and-sync`), а не ручной правкой их `package.json`; подготовка применена, и `pnpm ds:sync-versions --check` подтверждает согласованность версий в runtime, манифестах и реестре. Значения исходного дерева после подготовки: `@prism-system/ui-core` и обе тестовые системы — `2.0.0`, `@prism-system/tools` — `1.1.0` (базовая `1.0.0` плюс два существующих и один V4 minor-Changesets). Приватный корень Changesets не версионирует: его `0.4.0` выставлен отдельно после прохождения критериев фазы 5. Публикация не выполнялась — npm-публикации, git-тега, GitHub Release и коммита нет, поэтому версии в исходном дереве не являются выпущенными релизами. Колонка «До версии фазы 5» хранит историческую базу до этой подготовки.

## Фаза 1 — контракт V4 и источник истины

**Результат:** стабильные правила для 32 контрактов и токенов, на которых могут независимо строиться пакеты, инструменты и приложения.

1. Зафиксировать перечень 20 обязательных и 12 дополнительных контрактов из спецификации. Для каждого описать props, варианты, состояния, составные части, семантику HTML, клавиатуру и требования доступности. Особо определить `Link` (навигация), `FormField` (связь label/help/error), `Container` и `Stack` (токенизированная композиция), а также границы `Table` и `Pagination` без логики данных.
2. В `packages/core/src/contracts`, `packages/core/src/design-system` и публичных экспортах добавить V4-типы, список required/optional и helper для V4. `ui-core` остаётся без визуальных значений и CSS. Сохранить отдельное распознавание опубликованного V2-контракта там, где это требуется потребительским инструментам.
3. Утвердить схему `tokens.source.json`: смысловые цвета, типографика, шкала/роли отступов, ширины контейнеров, брейкпоинты, слои, радиусы, тени и движение. Явно задать обязательные поля, допустимые единицы, ссылки и правила светлой/тёмной темы. Добавить schema/descriptor для доступных компонентов, вариантов и частей.
4. Спроектировать `design-system.json` со `schemaVersion: 2` и `contract: "v4"`. В нём доступны только опубликованные capabilities, имена токенов, пути к CSS/Tailwind и документации; манифест не должен требовать исполнения кода для чтения каталога. Описать отдельные правила чтения V2/schema 1 и V4/schema 2.
5. Обновить валидацию схем и contract fixtures: 20 обязательных присутствуют, выбранные дополнительные согласованы с runtime-картой и экспортами, неизвестные имена отклоняются, отсутствующие дополнительные допустимы. Зафиксировать ожидаемые сообщения ошибок.

**Затрагивает:** `packages/core`, `schemas`, генерацию/валидацию манифеста в `scripts`, контрактную часть [спецификации](README.md).

**Готово, когда:** типовой V4 fixture с разными наборами дополнительных компонентов проходит проверку; отсутствие обязательного и ложная capability дают ошибку; опубликованный V2 fixture читается по прежним правилам; `ui-core` не содержит цветов, отступов и иных визуальных значений. Список 32 API описан настолько конкретно, чтобы фаза 2 не придумывала props по ходу переноса.

## Фаза 2 — единая архитектура и реальные системы

**Результат:** шаблон, System A и System B имеют одну структуру; каждая система реализует 20 обязательных компонентов и объявляет только свои дополнительные.

1. Перестроить `templates/design-system` по структуре из [спецификации](README.md#единая-структура-пакета): один каталог на компонент, локальные `*.tsx`, `*.css`, `index.ts`; отдельно `src/design-system.ts`, общий CSS-вход, токены и публичные экспорты. Составные части живут в каталоге своего компонента. Интерактивные модули сохраняют корректные `"use client"` границы.
2. Сделать детерминированную генерацию из `tokens.source.json` в TypeScript-токены и `tokens.css`; системные CSS-файлы читают созданные переменные. Bridge-файл Tailwind генерируется из того же источника, его подключение к опубликованному пакету проверяется в фазе 3.
3. Перевести System A и B с дублируемых TS/CSS-значений и крупных файлов `src/components/index.tsx` на эту структуру. Сохранить узнаваемый визуальный характер обеих систем и работоспособность 14 прежних компонентов; добавить `Heading`, `Text`, `Link`, `Container`, `Stack`, `FormField` и полные группы токенов.
4. Реализовать в системах разные подмножества дополнительных компонентов для проверки модели capabilities: **A** — `Grid`, `Fieldset`, `Alert`, `Progress`, `Accordion`, `Pagination`, `Table`; **B** — `Section`, `Alert`, `Skeleton`, `Toast`, `Avatar`, `Breadcrumbs`. Так все 12 видны хотя бы в одной тестовой системе, `Alert` проверяется в обеих, а отсутствие остальных — в каждой. Для выбранного компонента дать настоящий экспорт, CSS, runtime-запись, манифест и пример; ни одна система не обязана реализовать все 12.
5. Обновить `ds:create`, `ds:register`, `ds:manifest`, `ds:check`, `ds:sync-versions`, `ds:release` и связанные schema/registry paths. `ds:create` создаёт V4 по умолчанию; проверка выявляет устаревшие generated files, неправильную структуру, расхождение runtime/manifest/exports и пропущенный CSS.

**Затрагивает:** `templates/design-system`, `packages/system-a`, `packages/system-b`, `scripts`, `config`, `schemas`.

**Готово, когда:** новая система из `pnpm ds:create <id>` и обе существующие проходят build/typecheck/`ds:check`; 20 обязательных экспортируются и оформлены; варианты и реальные optional отражены в манифесте; пакет собирает один обычный `styles.css`; перенос существующих компонентов не внёс видимых регрессий в контрольные сценарии Showcase/Reference App.

## Фаза 3 — Tailwind bridge и `prism-ds`

**Результат:** опубликованный пакет работает с обычным CSS и с Tailwind v4, а пользователь получает единый понятный путь `search → info → use → check`.

1. Публиковать у каждой V4-системы `./tailwind.css` с `@theme inline`, созданным из тех же токенов, что `tokens.css`. Проверить порядок импортов, один выбранный bridge на сборку, работающие семантические utility-классы, статические брейкпоинты и токены в порталах. Обычное потребление через `styles.css` не требует Tailwind.
2. На базе существующего `packages/tools` обеспечить чтение V2 и V4 по их схемам. Расширить `info` описанием визуального направления, доступных компонентов и токенов; добавить офлайн-команды `components [name]`, `tokens [group]`, `check` и `setup-tailwind --css <file>` из [спецификации](README.md#prism-ds-как-основная-точка-входа).
3. Сделать `use` главным описанным сценарием; добавить явный `--tailwind --css <file>` после проверки prerequisites и `upgrade <package> <exact-version>` с проверкой изменений capabilities. Сохранить точные границы команд: `connect` не устанавливает зависимости, `setup-tailwind` меняет лишь указанный CSS в `--cwd`, `install`/`use`/`upgrade` используют фиксированный npm/pnpm путь и только они меняют зависимости.
4. Добавить `--dry-run` для изменяющих команд, стабильный `--json` и коды завершения для агентского использования; сохранить совместимое поведение уже существующих команд. Проверить идемпотентность CSS setup и отсутствие записей/сети у офлайн-команд. Обновить CLI help и `packages/tools/README.md`.

**Затрагивает:** package exports/build System A/B и шаблона, `packages/tools`, consumer fixture, манифест и CLI-документацию.

**Готово, когда:** потребитель из **упакованного** V4-пакета собирает страницу с Tailwind v4 и без Tailwind; CSS utility соответствует токену компонента; V2-пакет обслуживается прежними командами; `components`/`tokens`/`check` работают офлайн; `--dry-run` и повторный `setup-tailwind` не создают лишних изменений; package mutations ограничены явными командами.

## Фаза 4 — Showcase, Reference App и понятная документация

**Результат:** витрина честно показывает возможности каждой системы, а новый агент может использовать пакет по опубликованным инструкциям без чтения исходников монорепозитория.

1. Перестроить `apps/showcase` и генерацию `apps/*/app/registry.ts`: registry задаёт системы/маршруты, манифест — обещанные capabilities и варианты, runtime-карта — реальные компоненты. Валидация связывает эти три источника. Для каждого известного контракта есть явный renderer; optional рендерится только при наличии, а при сравнении отсутствие показано как недоступность.
2. Выводить Foundations из реальных токенов системы вместо захардкоженных демонстрационных значений. Сохранить `/showcase/<id>`, добавить ссылку на конкретный компонент; проверить темы, состояния, адаптивность, клавиатуру и порталы. `apps/reference-app` сохраняет фиксированную композицию обязательных компонентов и условно показывает доступные optional.
3. Переработать **всю активную документацию**: корневые `README.md`, `AGENTS.md`, `docs/guide.md`, README/AGENTS систем и шаблона, Showcase/Reference App, consumer fixture, release guide и три lifecycle skills. Обновить описания 14→20+12, `prism-ds`, CSS/Tailwind, структуру папок, версионирование и ссылки на архив.
4. Для каждой системы дать одинаковый маршрут: quickstart с обычным CSS и Tailwind, Foundations, фактический Components catalog с вариантами/состояниями/примерами, правила Usage. Каталог генерируется из descriptor/манифеста; визуальное объяснение и примеры проходят review. `AGENTS.md` ссылается на источник истины вместо ручного второго каталога.
5. Добавить рецепты контентной страницы, формы и страницы с данными: Prism оформляет универсальные части, продукт предоставляет данные, навигацию и действия. Проверка документации ловит битые локальные ссылки, отсутствующие обязательные разделы и расхождение каталога с экспортами.

**Затрагивает:** `apps/showcase`, `apps/reference-app`, `scripts/sync-design-system-apps.mjs`, `docs`, README/AGENTS пакетов, `skills`, consumer examples.

**Готово, когда:** Showcase автоматически отображает разные наборы optional у A/B и не обращается к отсутствующим компонентам; Foundations совпадают с опубликованными токенами; Reference App работает с обеими системами; новый агент по документации и упакованному пакету собирает контентную страницу и форму без локальных исходников репозитория.

## Фаза 5 — сквозная проверка и подготовка версии 0.4.0

**Результат:** V4 проверена на упакованных артефактах, версии согласованы, выпуск подготовлен без автоматической публикации.

1. Добавить `pnpm ds:check-v4`: собрать и упаковать core, A/B, свежую систему из V4-шаблона и `@prism-system/tools`; в изолированных consumer fixtures проверить обычный CSS, Tailwind v4, TS/public exports, 20 required, разные optional, манифест, `prism-ds` и идемпотентность. Отдельно прогнать опубликованный V2 fixture через новые consumer tools. Адаптировать `ds:check-v3` к статусу исторической проверки или сохранить его fixture неизменным и явно документировать назначение.
2. Прогнать `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm ds:check` для систем и релевантные сценарии приложений. Проверить контраст, фокус, клавиатуру, reduced motion, размеры экрана, порталы и отсутствие визуальной регрессии базовых компонентов. Убедиться, что `ds:release` отклоняет неполные токены/компоненты/манифест/bridge и ничего не публикует.
3. Подготовить migration notes для потребителя V2→V4: изменение контракта и манифеста, выбор optional, imports CSS/Tailwind, новые CLI-команды и точные версии. Обновить документацию выпуска и сверить все активные ссылки и примеры с результатом проверки.
4. Создать Changesets с корректными bump types, выполнить `pnpm version-packages-and-sync` и проверить итоговые версии, внутренние зависимости, runtime `DesignSystem.version`, manifest, registry и lockfile. Цели: core и A/B `2.0.0`, tools `1.1.0`; расхождения с таблицей требуют объяснения через фактическую совместимость до выпуска.
5. После успешных gates обновить приватный root `package.json` до `0.4.0`, повторить версионную и packed-проверку, составить итоговый release checklist. Публикация npm, git tag и GitHub Release выполняются отдельно по явному решению человека.

**Затрагивает:** `scripts/check-v4-lifecycle.mjs`, fixtures, Changesets/changelogs, package manifests/lockfile, root `package.json`, release docs.

**Готово, когда:** packed V4 и legacy V2 сценарии проходят, документация и фактический API совпадают, корень имеет `0.4.0`, все публикуемые пакеты и манифесты имеют согласованные версии, `git diff` содержит проверяемые migration notes и Changesets, а публикация не произошла.
