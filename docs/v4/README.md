# Prism — текущая спецификация

Документ описывает текущий продукт: единственный контракт компонентов (**версия 4**),
его источники истины, структуру пакета, мост к Tailwind и потребительский CLI.
Практический гайд — [../guide.md](../guide.md), примеры композиций —
[recipes.md](recipes.md), критерии качества и проверки — [quality.md](quality.md),
исторические этапы — [../archive/README.md](../archive/README.md).

## Контракт в одном абзаце

Prism даёт готовый визуальный язык для целого интерфейса: смысловые токены,
**29 обязательных компонентов**, каталог из **17 дополнительных контрактов**,
CSS-оформление в каждом пакете и мост к Tailwind для композиции продукта. Все пакеты
имеют одинаковую структуру исходников, одинаковый маршрут документации и проверяются
в Showcase, Reference App и на упакованном потребителе. `prism-ds` — основная точка
выбора, подключения, изучения, проверки и обновления системы. Продукт отвечает за
содержание страниц, данные, маршруты, действия и backend.

Контракт идентифицируется числовым `contractVersion: 4` в runtime
(`DesignSystem`) и в сгенерированном манифесте. Параллельных версий контракта и
строковых маркеров в текущем API нет.

## Состав контракта

**29 обязательных компонентов** — их обязана реализовать каждая система:

```text
Button, Input, Textarea, Card, Badge, Checkbox, RadioGroup, Switch, Select,
Tabs, Dialog, DropdownMenu, Tooltip, Separator, Heading, Text, Link, Container,
Stack, FormField, Center, Cluster, Sidebar, AspectRatio, Combobox, DatePicker,
NumberField, Slider, FileUpload
```

**17 дополнительных контрактов** — система реализует только те, которые действительно
предоставляет, и объявляет их в descriptor и манифесте:

| Дополнительный компонент | Назначение |
| --- | --- |
| `Grid` | Сетка на токенах системы |
| `Section` | Оформление и ритм секции |
| `Fieldset` | Группа связанных полей с заголовком |
| `Alert` | Встроенные сообщения и смысловые варианты |
| `Progress` | Известный или неопределённый прогресс |
| `Skeleton` | Ожидание содержимого |
| `Toast` | Краткое временное уведомление |
| `Accordion` | Раскрываемые секции |
| `Avatar` | Изображение или инициалы пользователя |
| `Breadcrumbs` | Путь по иерархии страниц |
| `Pagination` | Управление страницами набора данных |
| `Table` | Семантическое представление табличных данных |
| `Metric` | Компактный показатель с подписью и контекстом |
| `DescriptionList` | Пары «термин — описание» на нативных `dl`/`dt`/`dd` |
| `Timeline` | Упорядоченная последовательность событий |
| `Meter` | Измеренное значение в известном диапазоне |
| `EmptyState` | Нейтральная заглушка «данных пока нет» |

Дополнительный компонент — это реальная capability, а не заглушка. Отсутствие имени в
`components` манифеста означает «недоступен»; записей со значением `false` нет.
Для `Table` контракт покрывает только представление данных; загрузка, сортировка и
фильтрация остаются в продукте. Отдельный `Spinner` не вводится: неопределённое
состояние входит в `Progress`.

Категории манифеста группируют контракты по назначению. Это канонический перечень
принадлежности (`capabilities.categories`), одинаковый у всех систем и **не** список
доступности; категории охватывают не все контракты:

| Категория | Обязательные | Дополнительные |
| --- | --- | --- |
| `composition` | Container, Stack, Center, Cluster, Sidebar, AspectRatio | Grid, Section |
| `forms` | FormField, Combobox, DatePicker, NumberField, Slider, FileUpload | — |
| `data-display` | — | Table, Pagination, Progress, Metric, DescriptionList, Timeline, Meter, EmptyState |

Поддержку в конкретной системе по-прежнему определяет только наличие ключа в
`components` манифеста; доступность внутри категории выводится пересечением имён
категории с этими ключами.

## Архитектура и границы

- `@prism-system/ui-core` — **неоформленный фундамент**: контракты компонентов, типы,
  один `DesignSystem` и один реестр, утилиты, a11y-хелперы, общие хуки. Цветов,
  токенов, отступов и вариантов в нём нет.
- `@prism-system/ui-system-*` — **вся визуальная часть**: смысловые токены, CSS,
  варианты, состояния, анимация и реализации компонентов. Система зависит только от
  `@prism-system/ui-core`; кросс-импорты между системами запрещены.
- `apps/*` — только композиция: раскладка, размещение, эталонные сценарии. Приложения
  не переопределяют внешний вид и не копируют компоненты.
- `@prism-system/tools` — **публикуемый инструмент потребителя** (`prism-ds`). Он не
  зависит ни от `ui-core`, ни от конкретной системы и не читает исходники этого
  репозитория во время работы.

```text
apps/*  ──────────►  @prism-system/ui-system-*  ──────────►  @prism-system/ui-core
```

## Источники истины

- **Контракт.** `@prism-system/ui-core` владеет типами и единственной картой
  компонентов: `DesignSystemComponents`, `REQUIRED_COMPONENTS`,
  `OPTIONAL_COMPONENTS`, `defineDesignSystem` и `createDesignSystemRegistry`.
  `DesignSystem.contractVersion` — числовое `4`.
- **Манифест.** Каждый пакет публикует сгенерированный `design-system.json`
  (`schemaVersion: 4`, `contractVersion: 4`) по публичному пути `./manifest`. Он
  сообщает фактические обязательные и дополнительные компоненты, варианты, размеры,
  составные части, имена токенов, группы, пути к артефактам и канонический перечень
  категорий `capabilities.categories`, но не значения токенов. Текущая форма манифеста
  одна: инструменты требуют `schemaVersion: 4` и отклоняют schema 3, поэтому читатели
  schema 3 обновляются вместе с системой.
- **Descriptor системы.** Package-owned `design-system.source.json` остаётся
  `schemaVersion: 3` и является repository-only входом генератора. Он владеет
  вариантами, размерами, примерами, визуальными опциями, составными частями и путями
  к документации; блока `capabilities` в нём нет и не должно быть — категории и
  доступность генерируются в манифест. Core-контракт владеет только HTML-семантикой,
  состоянием/взаимодействием и обязательными составными частями.
- **Токены.** Визуальные значения живут в `tokens.source.json` каждой системы, а не в
  `ui-core`; значения не дублируются в манифесте.
- **Capabilities.** Источник — одна карта компонентов: все 29 обязательных ключей
  плюс только реально реализованные дополнительные. Runtime-карта, публичные экспорты,
  descriptor и манифест должны совпадать. Поддержку в конкретной системе даёт только
  наличие ключа в `components` манифеста; `capabilities.categories` — канонический
  перечень принадлежности категориям (`composition`, `forms`, `data-display`), а не
  второй список доступности: доступность внутри категории выводится пересечением её
  имён с ключами `components`, и категории не покрывают все контракты.

## Контракты компонентов (46 имён)

Ниже зафиксированы корневой элемент, ключевые props, составные части и требования к
состоянию, клавиатуре и ARIA для всех 46 контрактов. Общие правила:

- `ui-core` задаёт семантику, HTML-модель, состояние и обязательные составные части;
  визуальные варианты, размеры и примеры принадлежат descriptor каждой системы.
- Prop-объединения (`variant`, `size` и т. п.) остаются как есть. Общие core-контракты
  не определяют визуальные словари вариантов и размеров: фактические варианты,
  размеры и примеры объявляет descriptor каждой системы.
- Составные части крепятся статическими членами корня (`Dialog.Content`, `Card.Header`).
  Компоненты, которым нужны хуки или порталы, сохраняют границу `"use client"` в
  реализации системы.
- Все компоненты принимают нативные props своего корневого элемента, если не указано
  иное; `ui-core` не добавляет визуальных значений.

### Общие 14 компонентов

Точные типы — в `packages/core/src/contracts/*.ts`; ниже — актуальная семантика.

- **Button** — корень `<button>`; `variant?: "primary" | "secondary" | "outline" | "ghost" | "destructive" | "link"`, `size?: "sm" | "md" | "lg" | "icon"`, `loading?`, `fullWidth?`, `leftIcon?`, `rightIcon?`, `asChild?`. Составных частей нет. `loading` выставляет `aria-busy="true"` и сохраняет доступное имя; клавиатура нативная (`Enter`/`Space`).
- **Input** — корень `<input>`; `size?: "sm" | "md" | "lg"` (нативный числовой `size` исключён), `invalid?`, `startAdornment?`, `endAdornment?`. `invalid` выставляет `aria-invalid`. Составных частей нет.
- **Textarea** — корень `<textarea>`; `size?`, `invalid?`, `autoResize?`. Сохраняет нативную семантику, участие в форме и `aria-invalid`.
- **Card** — корень `<div>`; `variant?: "default" | "muted" | "outline" | "elevated" | "interactive"`, `padding?: "none" | "sm" | "md" | "lg"`, `asChild?`. Части: `Header` (`<div>`), `Title` (`<h3>`), `Description` (`<p>`), `Content` (`<div>`), `Footer` (`<div>`).
- **Badge** — корень `<span>`; `variant?: "default" | "secondary" | "success" | "warning" | "danger" | "info" | "outline"`, `size?: "sm" | "md"`, `dot?`, `asChild?`. Составных частей нет.
- **Checkbox** — корень `<button>` с `role="checkbox"`; `checked?: boolean | "indeterminate"`, `defaultChecked?`, `onCheckedChange?`, `disabled?`, `required?`, `name?`, `value?`, `invalid?`, `size?: "sm" | "md" | "lg"`. `aria-checked` поддерживает `"mixed"`; активация — `Space`/`Enter`.
- **RadioGroup** — корень `<div role="radiogroup">`; `value?`, `defaultValue?`, `onValueChange?`, `name?`, `form?`, `required?`, `disabled?`, `dir?`, `orientation?`, `loop?`. Части: `Item` (`<button role="radio">`, обязательный `value`), `Indicator` (`<span>`, `forceMount?`). Навигация стрелками внутри группы; `Indicator` попадает в дерево доступности только у выбранного элемента.
- **Switch** — корень `<button role="switch">`; `checked?`, `defaultChecked?`, `onCheckedChange?`, `disabled?`, `required?`, `name?`, `value?`, `invalid?`, `size?`. Части: `Thumb` (`<span>`, без взаимодействия). Тумблер доступен с `Space`/`Enter`, несёт `aria-checked`, доступное имя стабильно.
- **Select** — корень без собственного DOM (children-only); `value?`, `defaultValue?`, `onValueChange?`, `open?`, `defaultOpen?`, `onOpenChange?`, `disabled?`, `required?`, `name?`, `invalid?`, `placeholder?`. Части: `Trigger` (`<button>` + `asChild`, `role="combobox"`, `aria-expanded`/`aria-controls`, `size?`, `invalid?`, `placeholder?`), `Value`, `Content` (`<div>` с `position`/`side`/`align`/`forceMount`), `Group`, `Label`, `Item` (`<div>`, обязательный `value`, `textValue?`, `disabled?`), `Separator`. Модель listbox: `ArrowUp`/`ArrowDown`/`Home`/`End`/`Enter`/`Escape`.
- **Tabs** — корень `<div>`; `value?`, `defaultValue?`, `onValueChange?`, `orientation?`, `activationMode?: "automatic" | "manual"`, `dir?`. Части: `List` (`<div>`), `Trigger` (`<button>` + `asChild`, обязательный `value`), `Content` (`<div>`, обязательный `value`, `forceMount?`). Роли `tablist`/`tab`/`tabpanel` и навигация стрелками.
- **Dialog** — корень без собственного DOM (children-only); `open?`, `defaultOpen?`, `onOpenChange?`, `modal?`. Части: `Trigger` (`<button>` + `asChild`), `Close` (`<button>` + `asChild`), `Portal`, `Overlay` (`<div>`), `Content` (`<div>`, `role="dialog"`, `aria-modal="true"`, колбэки фокуса/Escape/outside), `Header`, `Footer`, `Title` (`<h2>`), `Description` (`<p>`). Захват фокуса, закрытие по `Escape`, возврат фокуса на триггер.
- **DropdownMenu** — корень без собственного DOM (children-only); `open?`, `defaultOpen?`, `onOpenChange?`, `modal?`, `dir?`. Части: `Trigger` (`<button>` + `asChild`, `aria-haspopup="menu"`), `Portal`, `Content` (`<div>` с позиционированием и колбэками), `Group`, `Label`, `Item` (`<div>`, `disabled?`, `textValue?`, `onSelect?`), `CheckboxItem`, `RadioGroup`, `RadioItem`, `ItemIndicator`, `Separator`, `Arrow`, `Sub`, `SubTrigger`, `SubContent`. Меню-модель: стрелки, `Home`/`End`, typeahead, `Enter`/`Space`, `Escape`; подменю и check/radio-элементы несут соответствующие роли и `aria-checked`.
- **Tooltip** — корень без собственного DOM (children-only); `open?`, `defaultOpen?`, `onOpenChange?`, `delayDuration?`, `disableHoverableContent?`. Части: `Provider` (общие задержки), `Trigger` (`<button>` + `asChild`, `aria-describedby`), `Portal`, `Content` (`<div>`, `role="tooltip"`, опциональный `aria-label`, закрытие по `Escape`), `Arrow`. Подсказка не должна быть единственным способом получить информацию.
- **Separator** — корень `<div>`; `orientation?: "horizontal" | "vertical"`, `decorative?`. При `decorative` убирается из дерева доступности; иначе несёт `role="separator"` и `aria-orientation`. Составных частей нет.

### Обязательные компоненты композиции

- **Heading** — корень `h1`–`h6` по **обязательному** `level: 1 | 2 | 3 | 4 | 5 | 6`; принимает нативные props заголовка. Визуальные размеры и стили задаёт система, не core. Составных частей нет; уровни должны образовывать последовательную иерархию страницы.
- **Text** — корень `<p>`; `as?: "p" | "span" | "div"` со значением по умолчанию `p`; принимает нативные props выбранного элемента. Стили и роли типографики — на стороне системы.
- **Link** — нативный `<a>` с **обязательным** `href`; остальное — нативные props (`rel`, `target`, `download` и т. п.). Система владеет визуальными вариантами; ссылка обязана иметь различимый текст или доступное имя, состояние фокуса видимо.
- **Container** — корень `<div>`; `as?: "div" | "main" | "section" | "article" | "aside"` со значением по умолчанию `div`. Ширины и центрирование берутся из токенов системы; core их не задаёт. Составных частей нет.
- **Stack** — корень `<div>`; `as?: "div" | "ul" | "ol"` (по умолчанию `div`), `direction?: "horizontal" | "vertical"` (по умолчанию `vertical`), `wrap?`. **Отступ между элементами (`gap`) в core не входит** — шаг задаёт система. При `as="ul"`/`"ol"` дочерние элементы должны быть `<li>`. Составных частей нет.
- **FormField** — корневая группа `<div>` с **обязательным** потребительским `id`; состояние `required`/`disabled`/`invalid` разделяется с составными частями `Label`, `Control`, `Description`, `Error`. `Control` поддерживает `asChild`, оборачивая существующий контрол системы; `Label` связывается через `htmlFor`, `Description`/`Error` — через `aria-describedby`, `invalid` выставляет `aria-invalid` на контроле, `required` — `aria-required`. `Error` объявляется вспомогательным технологиям (живой регион / `role="alert"`).

### Остальные обязательные контракты

- **Center** — корень `<div>`; только нативные props. Горизонтальное центрирование; пропов margin/padding/width и layout-шкал в контракте нет — выравнивание и отступы принадлежат системе. Составных частей нет, лендмарк-ролей не добавляет.
- **Cluster** — корень `<div>`; только нативные props. Переносимая inline-группа (теги, действия, чипы); `gap`/выравнивание остаются решением системы. Составных частей нет.
- **Sidebar** — корень `<div>`; только нативные props. Обёртка боковой области рядом с основным содержимым. Контракт **не** подразумевает лендмарк `aside`: если системе нужна роль complementary, она добавляет её явно. Ширина и отступы принадлежат системе.
- **AspectRatio** — корень `<div>`; `ratio?: number` — положительное число, по умолчанию `1`. Сохраняет пропорцию ширины к высоте; это единственный prop сверх нативной базы `div`, потому что пропорция структурна, а не декоративна. Контент (изображение, медиа) продукт размещает внутри; ролей нет.
- **Combobox** — корневой враппер `<div>` (children-only) плюс скрытый named input для формы; `value?`, `defaultValue?`, `onValueChange?`, `inputValue?`, `defaultInputValue?`, `onInputValueChange?`, `open?`, `defaultOpen?`, `onOpenChange?`, `disabled?`, `required?`, `requiredMessage?`, `invalid?`, `name?`. Части: `Input` (реальный focusable `<input>` с `role="combobox"`, `aria-expanded`/`aria-controls`, `aria-haspopup="listbox"`, `aria-autocomplete="list"`, `aria-activedescendant`), `Content` (listbox-попап), `Item` (опция с `aria-selected`, обязательный `value`, `disabled?`, `textValue?`). Клавиатура: `ArrowDown`/`ArrowUp` открывают попап и без зацикливания двигают активную опцию, `Enter` выбирает только активную доступную опцию, `Escape` закрывает без commit и сохраняет набранный запрос, `Tab` закрывает без блокировки фокуса. Правка `Input` после выбора немедленно инвалидирует выбранное значение (`onValueChange("")`); текст запроса — только фильтр/отображение, он никогда не становится значением и не удовлетворяет `required`. Фильтрация — условный рендер `Item` у продукта; core не выполняет асинхронный поиск.
- **DatePicker** — нативный `<input type="date">`; `type` фиксирован, `invalid?` выставляет `aria-invalid`. Нативные value/change/ref/form-семантика сохраняется; составных частей нет.
- **NumberField** — нативный `<input type="number">`; `type` фиксирован, `invalid?` выставляет `aria-invalid`. Нативные value/change/step/ref/form-семантика сохраняется; вид спиннера и кнопок шага — решение системы. Составных частей нет.
- **Slider** — нативный `<input type="range">`; `type` фиксирован, `invalid?` выставляет `aria-invalid`. Нативные `min`/`max`/`step`, клавиатура и form-семантика сохраняются; вид трека, ползунка и заливки — у системы. Составных частей нет.
- **FileUpload** — нативный `<input type="file">`; `type` фиксирован, `invalid?` выставляет `aria-invalid`. Нативные `accept`/`multiple`/`capture`/change/ref/form-семантика сохраняются. Dropzone и видимые списки файлов остаются композицией продукта или системы вокруг контрола, а не частью контракта.

### Семнадцать дополнительных контрактов

Реализуются только по выбору системы и публикуются как capability; пустые заглушки
запрещены.

- **Grid** — корень `<div>` только; пропорции и отступы раскладки (колонки, `gap`) в core не входят и задаются системой. Составных частей нет, ARIA-роли не добавляются.
- **Section** — семантический `<section>`; части: `Header` (`<div>`), `Title` (`<h2>`), `Description` (`<p>`), `Content` (`<div>`), `Footer` (`<div>`). `Title` — семантический заголовок секции. Размеры и ритм — у системы.
- **Fieldset** — нативный `<fieldset>`; часть: `Legend` (нативный `<legend>`). Сохраняет нативную группировку полей и доступность подписи группы.
- **Alert** — корень `<div>`; части: `Title` (`<h5>`), `Description` (`<p>`). Роль — `status` (вежливо, по умолчанию) или `alert` (настойчиво) через соответствующий prop; по умолчанию `status`. Визуальные смысловые варианты (info/success/warning/danger и т. п.) задаёт система.
- **Progress** — корень `<div role="progressbar">`; детерминированный при наличии `value` и неопределённый при его отсутствии, с `max`. **Обязательно доступное имя** (`aria-label` или `aria-labelledby`). Детерминированный несёт `aria-valuenow`/`aria-valuemin`/`aria-valuemax`, неопределённый их не выставляет. Визуальное оформление — у системы.
- **Skeleton** — декоративный корень `<div>`: `aria-hidden="true"`, без роли и доступного имени. Размеры и анимацию задаёт система; «кости» не объявляются скринридеру.
- **Toast** — части: `Provider`, `Viewport` (`<ol>`), `Root` (`<li>`), `Title` (`<h5>`), `Description` (`<p>`), `Action` (`<button>` + `asChild`, обязательный `altText`), `Close` (`<button>` + `asChild`). `duration` — положительное число или `null` (без авто-закрытия) на уровне провайдера/корня; статус по умолчанию вежливый (`status`). Таймер ставится на паузу при фокусе и наведении и возобновляется после. **Очерёдность, дедупликация и лимит числа toast — ответственность продукта, а не контракта.** Уведомление не должно перехватывать фокус; текст должен оставаться доступным и без визуального авто-закрытия.
- **Accordion** — корень `<div>` с дискриминируемым `type: "single" | "multiple"`; `single` использует строковый `value`/`onValueChange` и `collapsible?`, `multiple` — массив строк. Части: `Item`, `Header`, `Trigger`, `Content`. `Trigger` несёт `aria-expanded` и `aria-controls`, `Content` — `role="region"` и `aria-labelledby`; клавиатура: `Enter`/`Space` переключают триггер нативно, `ArrowUp`/`ArrowDown` перемещают фокус между триггерами аккордеона, `Home`/`End` ведут к первому/последнему, навигация зацикливается.
- **Avatar** — корень `<span>`; части: `Image` (`<img>` с **обязательным** `alt`) и `Fallback` (`<span>`, инициалы или заглушка, пока изображение недоступно или не загрузилось). Размеры и формы — у системы; доступное имя даёт `alt` или текст fallback.
- **Breadcrumbs** — именованный `<nav>` (обязательное доступное имя, например `aria-label`); части: `List` (`<ol>`), `Item` (`<li>`), `Link` (нативный `<a>`, обязательный `href`), `Current` (`<span>` текущей страницы с `aria-current="page"`, не ссылка). Переходы — нативными ссылками.
- **Pagination** — статичный URL-first `<nav>` с обязательным доступным именем; части: `List` (`<ul>`), `Item` (`<li>`), `Link` (ссылка с обязательным `href`, который предоставляет продукт), `Previous`, `Next` (ссылки с `href`), `Current` (`<span>` с обязательным `aria-current="page"`), `Ellipsis` (`<span>`, декоративный, `aria-hidden`). **Состояния пагинации в core нет:** продукт задаёт `href` и активную страницу.
- **Table** — нативный `<table>`; части: `Caption` (`<caption>`), `Header` (`<thead>`), `Body` (`<tbody>`), `Footer` (`<tfoot>`), `Row` (`<tr>`), `Head` (`<th>` со `scope`), `Cell` (`<td>`). Таблица должна иметь доступное имя (через `Caption` либо `aria-label`/`aria-labelledby`). **Логики данных нет:** сортировка, фильтрация и загрузка остаются в продукте.
- **Metric** — корень `<dl>`; части: `Label` (`<dt>`), `Value` (`<dd>`), `Description` (`<dd>`, опционально). Компактный статистический показатель: связь подписи и значения даёт нативная структура `dl`/`dt`/`dd`. Единицы, точность и формат — текст продукта; appearance-пропов нет.
- **DescriptionList** — корень `<dl>`; части: `Item` (`<div>`), `Term` (`<dt>`), `Description` (`<dd>`). Группирует термин с одним или несколькими описаниями; колонки, разделители и отступы — решения системы.
- **Timeline** — корень `<ol>`; части: `Item` (`<li>`), `Title` (`<h3>`), `Time` (нативный `<time>`, желателен machine-readable `dateTime`), `Description` (`<div>`). Порядок событий доступен вспомогательным технологиям даже при скрытых визуальных маркерах; рельс, маркеры и отступы — у системы.
- **Meter** — нативный `<meter>` для измеренного значения в известном диапазоне (например, заполнение диска или балл); это не индикатор прогресса — им владеет `Progress`. **Обязательное доступное имя** через `aria-label` или `aria-labelledby`; нативные `value`/`min`/`max`/`low`/`high`/`optimum` сохраняются, вид трека — у системы.
- **EmptyState** — корень `<div>` без роли и live-region: пустое состояние — обычный контент страницы, а не alert. Части: `Title` (`<h3>`), `Description` (`<p>`), `Action` (контейнер `<div>`, внутрь продукт ставит `Button` или `Link`). Иконки, иллюстрации и отступы — решения системы.

## Единая структура пакета

System A, System B и все новые системы используют один шаблон исходников. Каждая
запись контракта получает собственную папку; составные части (`Dialog.Trigger`,
`Card.Header` и т. п.) остаются рядом с корневым компонентом. Дополнительный
компонент использует точно такую же структуру, что и обязательный.

```text
packages/<system>/
├── AGENTS.md
├── README.md
├── USAGE.md
├── package.json
├── design-brief.json
├── design-system.source.json
├── tokens.source.json
├── design-system.json             # генерируемый манифест
└── src/
    ├── index.ts                   # стабильный публичный API и импорт CSS
    ├── design-system.ts           # идентичность и карта компонентов
    ├── components/
    │   ├── index.ts               # только публичные экспорты
    │   ├── button/
    │   │   ├── Button.tsx
    │   │   ├── button.css
    │   │   └── index.ts
    │   ├── dialog/
    │   │   ├── Dialog.tsx          # корень и связанные части
    │   │   ├── dialog.css
    │   │   └── index.ts
    │   └── ...                     # обязательные и выбранные дополнительные
    ├── styles/
    │   ├── index.css              # единый вход в CSS пакета
    │   ├── tokens.css             # генерируемые переменные
    │   └── tailwind.css           # генерируемый Tailwind-мост
    └── tokens/
        └── index.ts               # генерируемый публичный экспорт
```

`src/components/index.ts` и `src/styles/index.css` перечисляют только реально
реализованные компоненты в фиксированном порядке; они не содержат реализаций.
Генератор и валидатор синхронизируют их с `design-system.source.json`. Интерактивные
TSX-модули сохраняют собственную границу `"use client"`, когда она нужна. Сборка
публикует один обычный `styles.css` и отдельный `tailwind.css`; внутреннее разбиение
на файлы не меняет публичные импорты продукта.

`templates/design-system` сразу создаёт эту структуру для 29 обязательных
компонентов. Добавление дополнительного компонента создаёт папку по тем же правилам и
обновляет descriptor, публичные экспорты и CSS-вход. Валидатор проверяет наличие
папки, TSX, CSS и экспорта для каждого заявленного компонента.

## Полные токены из одного источника

Каждый пакет имеет декларативный `tokens.source.json` и схему для него. Из этого
файла детерминированно создаются публичный TypeScript-экспорт токенов, CSS-переменные
и Tailwind-мост; компонентные CSS-стили ссылаются на созданные переменные.
`pnpm ds:check <id>` обнаруживает расхождение исходных токенов и созданных файлов.

Схема `tokens.source.json` (`schemaVersion: 1`) закрепляет обязательные группы:

| Группа | Содержание |
| --- | --- |
| `themes` | светлая и тёмная темы; обе определяют одно и то же обязательное семантическое дерево цветов: `text`, `surface`, `border`, `action`, `status` |
| `typography` | семейства, размеры, веса, высота строки, межбуквенный интервал |
| `spacing` | шкала и смысловые роли отступов |
| `containers` | ширины контейнеров |
| `breakpoints` | статические брейкпоинты сборки |
| `layers` | z-слои |
| `radius` | радиусы |
| `shadow` | тени |
| `motion` | длительности и кривые движения |

Правила значений и ссылок:

- Каждая группа задаёт именованные значения; размеры несут явную единицу, а не «голое»
  число. Общие размеры используют `px|rem|em|ch|vw|vh|%`; брейкпоинты — только
  `px|rem|em`; длительности — `ms|s`. Отрицательные размеры отклоняются, кроме случаев,
  где они явно разрешены (например, межбуквенный интервал).
- Алиас — объект с единственным ключом `{"$ref": "<dot.path>"}`. Валидатор разрешает
  ссылки и отклоняет отсутствующие, циклические и несовместимые по типу.
- Значения должны быть безопасными CSS-токенами; брейкпоинты статичны на время сборки,
  runtime-токенов нет.
- Визуальные значения остаются в пакете системы, не в `ui-core`; манифест публикует
  только имена токенов, группы и пути к артефактам. Манифест — единственный источник
  контракта именования: `tokens.names.cssVariablePrefix` задаёт префикс CSS-переменных
  (например, `maivand-a` для `--maivand-a-color-text-primary`), а
  `tokens.names.tailwindUtilityPrefix` — пространство имён Tailwind-утилит (например,
  `prism` для `--color-prism-text-primary`). Оба значения генерируются из тех же
  констант, что и сами артефакты, поэтому потребитель не угадывает префиксы, а берёт
  их из манифеста.

## Tailwind-мост

Каждый пакет публикует отдельный CSS-подпуть `./tailwind.css` для Tailwind CSS v4.
Он объявляет смысловые utility-токены через `@theme inline`, ссылаясь на CSS-переменные
этой системы. Например, `--color-prism-surface` создаёт `bg-prism-surface`; цвета и
другие визуальные значения берутся из того же источника, что и компоненты.
[Документация Tailwind по темам и `@theme inline`](https://tailwindcss.com/docs/theme).

Потребитель Tailwind импортирует `tailwindcss`, затем `<package>/tailwind.css` и
`<package>/styles.css`. Потребитель без Tailwind использует компоненты и обычные
CSS-переменные без зависимости от Tailwind. Мост — обязательный артефакт каждого
пакета; Tailwind не становится зависимостью `ui-core` или runtime UI-пакета.

**Стили компонентов:** CSS с токенами оформляет сами UI-пакеты; Tailwind используется
в продукте для композиции и в мосте для доступных агенту utility-классов. Полный
перенос компонентных стилей в Tailwind не входит в продукт.
[Документация Tailwind о сканировании зависимостей](https://tailwindcss.com/docs/detecting-classes-in-source-files).

Брейкпоинты генерируются как значения для сборки CSS: их нельзя менять переключением
класса во время работы страницы. Один consumer build подключает мост одной выбранной
системы. Showcase проверяет системы по отдельности, чтобы глобальные имена
Tailwind-тем не конфликтовали. Порталы (`Dialog`, `Tooltip`, меню) также получают
правильные токены. Адаптер для Tailwind v3 не входит в продукт: мост рассчитан на
Tailwind v4.

## Реестр, создание и манифест

- `config/design-systems.json` — реестр зарегистрированных систем и маршрутов.
- `pnpm ds:create <id>` — генерация нового пакета из `templates/design-system`
  (29 обязательных компонентов, источник токенов, descriptor, документация) и его
  регистрация.
- `pnpm ds:register <id>` — регистрация или синхронизация пакета: маршруты,
  зависимости и tool-owned wiring приложений.
- `pnpm ds:manifest <id> [--write]` — проверка или пересборка сгенерированных
  токен-артефактов и `design-system.json`.
- `pnpm ds:check <id>` — валидация пакета: обязательные компоненты, заявленные
  дополнительные, runtime/manifest/exports/capabilities, CSS и bridge.
- `pnpm ds:sync-versions [id] [--check]` — выравнивание версий runtime, манифеста и
  реестра; `package.json.version` — авторитетный источник.
- `pnpm ds:release <id> --approved` — подготовка релиза: валидация, сборка, упаковка,
  Changeset. Никогда не версионирует и не публикует.

Парсер версии и генератор манифеста читают `src/design-system.ts`. Сгенерированный
манифест получает `schemaVersion: 4` и числовое `contractVersion: 4`, а package-owned
descriptor `design-system.source.json` остаётся `schemaVersion: 3`; другие формы
отклоняются. Блок `capabilities.categories` генерируется детерминированно из
канонического перечня категорий: его не редактируют вручную в манифесте и не дублируют
в descriptor. Отсутствие ключа дополнительного компонента означает «недоступен»;
поддержка внутри категории выводится пересечением имён категории с ключами
`components`. Валидатор требует все 29 обязательных компонентов, проверяет каждый
заявленный дополнительный и отклоняет неизвестные имена. Showcase и Reference App
показывают дополнительные компоненты только там, где они есть.

Текущая форма манифеста одна. Инструменты требуют `schemaVersion: 4` и отклоняют
schema 3: старый `prism-ds` и другие читатели schema 3 обновляются вместе с системой,
иначе они не прочитают новый манифест, а новый инструмент не примет старый.

## `prism-ds` — точка входа потребителя

CLI сохраняет явные границы и предоставляет стабильный `--json`, коды завершения и
сообщения с причиной и следующим действием. Справка ведёт по сценарию
`search → info → use → check`.

| Команда | Что даёт пользователю | Граница действия |
| --- | --- | --- |
| `prism-ds search [query...]` | Поиск визуального направления, версий и компонентов | Явная сеть, только чтение |
| `prism-ds info <package-or-id> [version]` | Краткий обзор визуального направления, версии, 29 обязательных и фактически доступных дополнительных компонентов, токенов и ссылок на документацию/Showcase | Явная сеть, только чтение |
| `prism-ds components [name] --cwd <root>` | Офлайн-каталог установленной системы: доступность, варианты, части компонента и ссылка на пример | Только чтение манифеста, без выполнения кода пакета |
| `prism-ds tokens [group] --cwd <root>` | Имена смысловых токенов и соответствие артефактам: префикс CSS-переменных берётся из `tokens.names.cssVariablePrefix`, пространство имён Tailwind-классов — из `tokens.names.tailwindUtilityPrefix`; значения токенов не публикуются | Офлайн, только чтение манифеста |
| `prism-ds setup-tailwind --cwd <root> --css <file> [--dry-run\|--check]` | Проверяет установленный Tailwind v4 и явно, повторяемо добавляет импорты `tailwind.css` и `styles.css` в указанный CSS-файл; `--dry-run` показывает план, `--check` требует уже правильных импортов | Офлайн; меняет только явно названный файл внутри продукта, не устанавливает зависимости |
| `prism-ds use <package-or-id> [version] --cwd <root>` | Установка и подключение одной явно выбранной системы; с `--tailwind --css <file>` дополнительно выполняет Tailwind setup; `--dry-run` резолвит цель, команду менеджера и план CSS без записи | Сеть и изменение зависимостей только по явной команде |
| `prism-ds check --cwd <root> [--css <file>]` | Офлайн-отчёт о потребителе: согласованность конфигурации, публичный экспорт `styles.css` и заявленного Tailwind-моста, prerequisites Tailwind v4, strict usage и доступность обязательных/дополнительных компонентов | Офлайн, только чтение; порядок импортов проверяется только при явном `--css` |
| `prism-ds upgrade <package> <version> --cwd <root> [--dry-run]` | Сравнивает установленный и выбранный точный релиз, сообщает об исчезнувших/добавленных компонентах и токенах, затем явно обновляет и переподключает пакет | Явная сеть и изменение зависимостей через тот же фиксированный npm/pnpm путь, что и `use` |

Изменяющие команды `install`, `use` и `upgrade` поддерживают `--dry-run`: он
показывает точную версию, команду package manager и планируемые изменения файлов без
записи и без запуска менеджера. Ошибка после успешной установки не маскируется
откатом, а указывает, на каком шаге процесс остановился.

Строгие границы: поиск и изучение релизов только читают сеть; `components`, `tokens`,
`doctor`, `check-usage` и `check` работают офлайн; `connect` меняет только consumer
config и инструкции; `setup-tailwind` меняет только явно выбранный CSS-файл;
зависимости меняют только `install`, `use` и `upgrade`. Команд `prism-ds publish`,
скрытого выбора системы и автоматической генерации страниц нет.

## Showcase и Reference App

`config/design-systems.json` определяет зарегистрированные системы и маршруты.
Установленный манифест каждой системы определяет, **какие компоненты и варианты она
обещает**, а runtime `DesignSystem.components` даёт реальные React-компоненты.
Проверка сопоставляет манифест, runtime-карту и публичные экспорты; отсутствие
заявленного компонента — ошибка валидации, а не пустая карточка в UI.

Showcase показывает Foundations из реальных токенов пакета: цвета, типографику,
отступы, контейнеры, радиусы, тени и движение. Для компонентов Showcase строит каталог
из 29 обязательных и только тех дополнительных, которые перечислены в манифесте
выбранной системы. На странице сравнения отсутствующий дополнительный компонент
обозначается как недоступный, а не пытается рендериться.

Демонстрации остаются явными проверочными сценариями приложения: для каждого
известного контракта есть renderer с вариантами, состояниями и доступностью; манифест
выбирает применимые сценарии, но не генерирует JSX вслепую. При добавлении нового
контракта validator требует сценарий, а для выбранного дополнительного компонента —
рабочий пример. Маршруты `/showcase/<id>` и переключение систем сохраняются; Showcase
владеет только расположением и сценариями и не переопределяет стили компонентов.

Reference App остаётся фиксированной композицией обязательных компонентов.
Дополнительные компоненты проверяются условными сценариями по capabilities системы без
изменения основной структуры страницы.

## Проверка и границы

Каждый пакет имеет одинаковый маршрут документации: `README.md` (что это, установка,
quickstart с обычным CSS и Tailwind, первый экран), Foundations из реальных токенов,
Components из фактического манифеста, Usage rules и `AGENTS.md` с машинными
инструкциями. Каталог, варианты и доступность дополнительных компонентов строятся из
descriptor и сгенерированного манифеста; примеры и объяснение визуального замысла
проходят review.

Проверки репозитория:

```bash
pnpm ds:check <id>     # пакет: контракт, манифест, exports, CSS, bridge
pnpm ds:check-tools    # prism-ds и манифесты на упакованных артефактах
pnpm ds:check-docs     # активная документация и локальные ссылки
pnpm ds:check-all      # полный приёмочный прогон по собранным артефактам
```

`ds:check-all` собирает и упаковывает core, системы, свежий пакет из шаблона и
`@prism-system/tools`, проверяет публичные экспорты, манифесты, токены, обычный CSS и
Tailwind v4 в изолированном потребителе и убеждается, что release preparation
fail-closed и ничего не публикует. Публичная граница для потребителя — единственная
текущая форма манифеста (`schemaVersion: 4`), схема компонента и fail-closed
поведение; точные тексты диагностик не являются отдельной API-гарантией.

Ручной review проверяет то, что не доказывают автоматические проверки: клавиатуру,
фокус, доступные имена, состояния loading/empty/error/success, адаптивность,
reduced motion и контраст. Peer ranges в package metadata не доказывают совместимость
каждой комбинации React 18/19 и зависимостей; новые или рискованные комбинации требуют
отдельной проверки.

Постоянные гарантии:

- у продукта один текущий контракт: ровно 29 обязательных компонентов и только
  реализованные дополнительные, объявленные системой; пустые заглушки недопустимы;
- пакет системы владеет токенами и визуальным оформлением; `tokens.source.json` —
  источник визуальных значений; `ui-core` остаётся неоформленной общей основой;
- изменение несовместимого публичного API требует Changeset и документации миграции;
- подготовка релиза проверяет и упаковывает артефакт, но не публикует его. Решение о
  публикации принимается отдельно.
