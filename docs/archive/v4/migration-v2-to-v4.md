# Миграция продукта с V2 на V4

> **Архив истории.** Практический маршрут перехода потребителя с прежнего контракта
> на текущий (версия 4). Документ сохранён как историческая запись: актуальная
> документация — [../../v4/README.md](../../v4/README.md) и
> [../../guide.md](../../guide.md), а команды и версии ниже — исторические
> (часть из них переименована).

Практический маршрут для продукта-потребителя, который переходит с V2-системы
(манифест `schemaVersion: 1`, `contract: "v2"`, 14 компонентов) на V4-систему
(манифест `schemaVersion: 2`, `contract: "v4"`, 20 обязательных плюс только
реально объявленные дополнительные компоненты). Ниже описана публичная граница:
продукт читает манифест `./manifest`, использует публичные импорты и команды
`prism-ds` и не заглядывает во внутренние файлы пакета.

Целевое поведение — в [текущей спецификации](../../v4/README.md), фазы и
подготовленные версии — в [плане этапа V4](PLAN.md), общий гайд по репозиторию — в
[гайде для человека](../../guide.md), практические примеры композиций — в
[рецептах потребителя](../../v4/recipes.md).

## Что меняется

**Контракт.** Публичный API 14 действующих компонентов V2 (`Button`, `Input`,
`Textarea`, `Card`, `Badge`, `Checkbox`, `RadioGroup`, `Switch`, `Select`, `Tabs`,
`Dialog`, `DropdownMenu`, `Tooltip`, `Separator`) сохраняется без изменений и
входит в 20 обязательных компонентов V4. Существующие вызовы этих компонентов
переписывать не нужно. V4 добавляет шесть обязательных компонентов — `Heading`,
`Text`, `Link`, `Container`, `Stack`, `FormField` — и до 12 дополнительных
контрактов, которые система реализует по выбору.

**Манифест.** Читатель строго различает две пары: `(schemaVersion: 1,
contract: "v2")` — прежняя схема, `(schemaVersion: 2, contract: "v4")` — новая.
Любая другая пара отклоняется. Продукт и агент читают публичный путь `./manifest`
и берут состав из него; по имени пакета или прежней версии нельзя предполагать,
что дополнительный компонент существует.

**Capabilities.** Карта компонентов V4 содержит все 20 обязательных ключей и
только реально реализованные дополнительные. Отсутствие ключа означает
«недоступен»: отдельного списка capabilities и записей со значением `false` нет,
пустые заглушки запрещены. Поэтому один и тот же продукт на System A и System B
использует общие 20 обязательных компонентов, а дополнительные подключает только
там, где система их объявила. Наборы тестовых систем различаются: System A
объявляет `Grid`, `Fieldset`, `Alert`, `Progress`, `Accordion`, `Pagination`,
`Table`, а System B — `Section`, `Alert`, `Skeleton`, `Toast`, `Avatar`,
`Breadcrumbs`. Это различие реальных возможностей, а не пробел в манифесте.

**CSS и токены.** Пакет публикует обычный `styles.css` и мост `tailwind.css`,
созданные из одного источника токенов. Для продукта без Tailwind ничего не
меняется: одного импорта `styles.css` достаточно. Порядок импортов для Tailwind
v4 и экспорт токенов описаны ниже.

**Команды.** Прежние сценарии `search` → `info` → `install`/`use` → `connect` →
`check-usage` сохраняются. Добавляются офлайн-команды `components`, `tokens`,
`check`, `setup-tailwind` и явный `upgrade` до точной версии.

## Версии пакетов

В таблице слева — база до версии фазы 5, справа — подготовленная версия в
исходном дереве этого репозитория. Подготовленные значения совпадают с текущими
`package.json`, но **опубликованными релизами не являются**: npm-публикации,
git-тега и GitHub Release не было.

| Пакет | До версии фазы 5 | Подготовленная версия (исходное дерево) |
| --- | --- | --- |
| Приватный корень репозитория | `0.3.0` | `0.4.0` |
| `@prism-system/ui-core` | `1.0.0` | `2.0.0` |
| `@prism-system/ui-system-a`, `@prism-system/ui-system-b` | `1.1.0` | `2.0.0` |
| `@prism-system/tools` | `1.0.0` | `1.1.0` |

Подготовленная `1.1.0` для `@prism-system/tools` складывается из базовой `1.0.0`
и minor-Changesets (два существующих и один V4); для `ui-core` и систем применены
major-Changesets. Версии применены командой `pnpm version-packages-and-sync`,
приватный корень обновлён до `0.4.0` отдельно (Changesets его не версионирует), а
`pnpm ds:sync-versions --check` подтверждает согласованность runtime, манифестов и
реестра.

Переход продукта на V4 — мажорное обновление системы (`1.1.0` → `2.0.0`): меняется
форма публичного манифеста и набор возможностей. Обновляйте зависимость до
**точного** номера опубликованного V4-релиза; использовать подготовленную версию
`2.0.0` в продукте до её публикации недопустимо — из npm она пока недоступна.

Changesets и синхронизация версий **подготовлены и применены**:
`pnpm version-packages-and-sync` выполнена, `pnpm ds:sync-versions --check`
проходит. Публикация же **не выполнялась**: npm-публикация, git tag и GitHub
Release остаются отдельными действиями человека, и этот документ их не запускает
и не заменяет release checklist. Пока V4 не опубликована, номера зависимостей в
продукте не меняются на подготовленные версии.

## Путь миграции

1. **Убедитесь, что V4-релиз опубликован.** Изучите пакет по сети (только чтение):

   ```bash
   npx prism-ds info @prism-system/ui-system-a --json
   npx prism-ds info @prism-system/ui-system-a <exact-version> --json
   ```

   Проверьте точную версию, `prismSystem.contract` = `"v4"`, наличие
   `exports["./manifest"]` и корректность манифеста. Если у системы ещё нет
   V4-релиза, миграцию начинать не с чем.

2. **Обновите зависимость до точной версии.** Только `install`, `use` и `upgrade`
   меняют зависимости продукта, и только по явной команде:

   ```bash
   npx prism-ds upgrade @prism-system/ui-system-a <exact-version> --cwd . --dry-run
   npx prism-ds upgrade @prism-system/ui-system-a <exact-version> --cwd .
   ```

   `upgrade` перед изменением сравнивает прежний и новый манифесты и сообщает об
   исчезнувших и добавленных компонентах и токенах. Если используемый
   дополнительный компонент пропал, замените его композицией из обязательных или
   выберите систему, которая его объявляет.

3. **Переподключите конфиг потребителя.** Команда `connect` работает офлайн и
   пишет только `.design-system/config.json` и инструкции в `AGENTS.md`:

   ```bash
   npx prism-ds connect @prism-system/ui-system-a --cwd .
   npx prism-ds doctor --cwd .
   ```

   Точная версия в конфиге, установленном `package.json` и манифесте должна
   совпадать; `doctor` проверяет это только чтением.

4. **Сверьте фактические возможности системы.** Каталог берётся из манифеста,
   ничего не угадывается:

   ```bash
   npx prism-ds components --cwd .
   npx prism-ds components Alert --cwd .
   ```

   Не выводите дополнительные компоненты из документации, имени системы или
   версии: только из `./manifest` и этого каталога.

5. **Переведите CSS.** Для продукта без Tailwind импорт `styles.css` остаётся
   единственным шагом. Для Tailwind v4 подключите мост в правильном порядке (см.
   раздел «CSS и Tailwind»).

6. **Внедрите новые обязательные компоненты там, где это полезно.** `Heading`,
   `Text`, `Link`, `Container`, `Stack`, `FormField` заменяют ручную разметку и
   самодельные связки label/описание/ошибка (см. «Примеры до и после»).

7. **Проверьте продукт.** Офлайн-команды читают только файлы продукта:

   ```bash
   npx prism-ds check --cwd . --css app/globals.css
   npx prism-ds check-usage --cwd .
   ```

   `check` сверяет конфиг, публичные CSS/bridge-экспорты, prerequisites Tailwind
   v4, строгое использование и доступность обязательных и дополнительных
   компонентов. `check-usage` ищет обходы дизайн-системы: произвольные
   цвета/радиусы/тени, визуальные inline-стили, локальные дубликаты компонентов.

8. **Примите релиз в репозитории (мейнтейнер).** Приёмочная проверка фазы 5 —
   мейнтейнерская команда `pnpm ds:check-v4`: она собирает и упаковывает core,
   System A/B, свежую систему из шаблона и `@prism-system/tools` и прогоняет
   изолированные consumer fixtures (обычный CSS, Tailwind v4, публичные экспорты,
   20 обязательных, разные наборы дополнительных, манифест, `prism-ds`,
   идемпотентность). Команда ничего не публикует и не меняет продукт.

## CSS и Tailwind

**Обычный CSS.** Один публичный импорт, как и раньше:

```tsx
import "@prism-system/ui-system-a/styles.css";
```

**Tailwind v4.** Порядок импортов обязателен: сначала `tailwindcss`, затем мост
**выбранной** системы, затем её обычный CSS:

```css
@import "tailwindcss";
@import "@prism-system/ui-system-a/tailwind.css";
@import "@prism-system/ui-system-a/styles.css";
```

Этот блок детерминированно добавляет `prism-ds setup-tailwind`, он же проверяет
уже установленный порядок (`--check`) и повторяется идемпотентно. Мост даёт
смысловые utility-классы для композиции страницы (например,
`bg-prism-surface`); внешний вид компонентов остаётся в `styles.css`, и
переопределять его классами моста нельзя. Одна сборка подключает мост одной
системы; адаптер для Tailwind v3 не поддерживается.

**Токены.** Публичный экспорт токенов — отдельный подпуть пакета:

```tsx
import { systemATokens } from "@prism-system/ui-system-a/tokens";
```

Имена и группы токенов показывает офлайн-команда `prism-ds tokens [group]`.
Префикс CSS-переменных и пространство имён Tailwind-утилит не угадываются, а
берутся из манифеста: `tokens.names.cssVariablePrefix` (например, `maivand-a`) и
`tokens.names.tailwindUtilityPrefix` (например, `prism`). Манифест публикует
имена токенов, группы и пути к артефактам, но не их значения: значения живут в
пакете системы, а не в `ui-core` и не в продукте.

## Примеры до и после

Всё ниже использует только публичные импорты: корень пакета, `styles.css`,
`tailwind.css`, `tokens` и `./manifest`. Внутренние пути пакета не импортируются.

**До (V2): ручная подпись и разметка.** Код с 14 компонентами V2 продолжает
работать и после обновления.

```tsx
import { Button, Card, Input } from "@prism-system/ui-system-a";
import "@prism-system/ui-system-a/styles.css";

export function SaveCardV2() {
  return (
    <Card>
      <Card.Header>
        <Card.Title>Сохранить изменения</Card.Title>
      </Card.Header>
      <Card.Content>
        <label htmlFor="title">Название</label>
        <Input id="title" />
        <Button variant="primary">Сохранить</Button>
      </Card.Content>
    </Card>
  );
}
```

**После (V4): те же компоненты плюс связи `FormField` и ритм `Stack`.**

```tsx
import { Button, Card, FormField, Input, Stack } from "@prism-system/ui-system-a";
import "@prism-system/ui-system-a/styles.css";

export function SaveCardV4() {
  return (
    <Card>
      <Card.Header>
        <Card.Title>Сохранить изменения</Card.Title>
      </Card.Header>
      <Card.Content>
        <Stack>
          <FormField id="title" required>
            <FormField.Label>Название</FormField.Label>
            <FormField.Control asChild>
              <Input />
            </FormField.Control>
          </FormField>
          <Button variant="primary">Сохранить</Button>
        </Stack>
      </Card.Content>
    </Card>
  );
}
```

`FormField` связывает подпись, описание и ошибку (`htmlFor`,
`aria-describedby`, `aria-invalid`, `aria-required`), а `Stack` задаёт
вертикальный ритм из токенов системы.

**До: разметка страницы вручную.**

```tsx
export function ArticleLead({ title, lead }: { title: string; lead: string }) {
  return (
    <main>
      <h1>{title}</h1>
      <p>{lead}</p>
    </main>
  );
}
```

**После: обязательные компоненты V4 берут ширину, типографику и ритм из системы.**

```tsx
import { Container, Heading, Stack, Text } from "@prism-system/ui-system-a";
import "@prism-system/ui-system-a/styles.css";

export function ArticleLead({ title, lead }: { title: string; lead: string }) {
  return (
    <Container as="main">
      <Stack>
        <Heading level={1}>{title}</Heading>
        <Text>{lead}</Text>
      </Stack>
    </Container>
  );
}
```

**Дополнительные компоненты — только по манифесту.** Импорт компонента, которого
нет в capabilities установленной системы, ломает сборку. Сначала проверьте
манифест, затем используйте компонент:

```bash
# «есть» или «нет» — из каталога установленной системы, офлайн
npx prism-ds components Table --cwd .
```

```tsx
// Только если система объявила Table; иначе собирайте блок из обязательных
// компонентов (Card, Stack, Badge, Text, Pagination и т. п. — по манифесту).
import { Table } from "@prism-system/ui-system-a";
```

**Обновление зависимости.** Номер справа — подготовленная в исходном дереве
версия; в продукте он появится только после реальной публикации V4.

```diff
- "@prism-system/ui-system-a": "^1.1.0"
+ "@prism-system/ui-system-a": "<exact-v4-version>"
```

## Команды prism-ds и их границы

| Команда | Назначение | Граница |
| --- | --- | --- |
| `prism-ds search [query...]` | Найти опубликованные системы | Сеть, только чтение |
| `prism-ds info <package-or-id> [version]` | Изучить манифест и contract релиза | Сеть, только чтение |
| `prism-ds install <package-or-id> [version] --cwd <root>` | Явно установить систему | Сеть + изменение зависимостей |
| `prism-ds use <package-or-id> [version] --cwd <root>` | Установить и подключить одной командой | Сеть + изменение зависимостей |
| `prism-ds upgrade <package-or-id> <exact-version> --cwd <root>` | Сравнить манифесты и обновить до точной версии | Сеть + изменение зависимостей |
| `prism-ds components [name] --cwd <root>` | Каталог компонентов установленной системы: обязательные, реальные дополнительные, варианты, части | Офлайн, только чтение манифеста |
| `prism-ds tokens [group] --cwd <root>` | Имена токенов, их группы и префиксы CSS/Tailwind; значения не публикуются | Офлайн, только чтение манифеста |
| `prism-ds check --cwd <root> [--css <file>]` | Сводный отчёт о продукте; порядок импортов проверяется только при явном `--css` | Офлайн, только чтение |
| `prism-ds setup-tailwind --cwd <root> --css <file>` | Добавить мост Tailwind v4 в указанный CSS; идемпотентно | Офлайн; меняет только названный файл, зависимости не ставит |
| `prism-ds connect [package] --cwd <root>` | Настроить конфиг потребителя и инструкции | Офлайн; пишет только consumer-конфиг |
| `prism-ds check-usage --cwd <root>` | Строгая проверка использования дизайн-системы | Офлайн, только чтение |
| `prism-ds doctor [package] --cwd <root>` | Диагностика: пакет, версия, манифест, конфиг | Офлайн, только чтение |
| `pnpm ds:check-v4` (репозиторий, мейнтейнер) | Приёмка фазы 5 на упакованных артефактах | Инструмент репозитория; не публикует и не меняет продукт |

Итого границы: `search` и `info` — единственное сетевое чтение; `install`,
`use` и `upgrade` — единственные команды, меняющие зависимости продукта;
`connect` меняет только consumer config и инструкции; `setup-tailwind` — только
явно названный CSS-файл; `components`, `tokens`, `check`, `check-usage`, `doctor` и
`pnpm ds:check-v4` ничего не меняют в продукте. У изменяющих команд есть
`--dry-run`; у команд для агентов и CI — стабильный `--json` и коды завершения.
`prism-ds publish`, скрытый выбор системы и автоматическая генерация страниц
отсутствуют.

## Версионирование и выпуск

Версионирование и публикация — **ручные, управляемые человеком** шаги через
Changesets:

```text
Изменение в коде
   ↓
pnpm changeset                # человек описывает изменение
   ↓
CI готовит version PR         # изменения версий + синхронизация
   ↓
ревью и merge PR              # человек одобряет
   ↓
workflow публикации           # защищённое окружение, OIDC
   ↓
пакет в npm
```

На момент написания миграции:

- подготовленные версии применены в исходном дереве: `package.json` содержат
  `2.0.0` у `ui-core` и систем, `1.1.0` у `@prism-system/tools`, приватный корень —
  `0.4.0`; **опубликованы** эти значения не были;
- Changesets применены командой `pnpm version-packages-and-sync`: major для
  `ui-core` и систем, minor для `@prism-system/tools`;
- приватный корень обновлён до `0.4.0` отдельно (Changesets его не версионирует),
  а `pnpm ds:sync-versions --check` проходит;
- V4 **не опубликована**, поэтому в продукте нет и не должно быть зависимости на
  V4-версию; точная версия для `upgrade` берётся только из реестра npm;
- `pnpm ds:release <id> --approved` в этом репозитории только готовит релиз
  (валидирует, собирает, упаковывает, создаёт Changeset) и никогда не
  версионирует и не публикует;
- публикация, git tag и GitHub Release — отдельное явное решение человека и на
  момент написания не выполнены.

Когда релиз состоится, версия установленного пакета, `DesignSystem.version`,
сгенерированный `design-system.json` и запись в `config/design-systems.json`
должны совпадать; расхождения устраняет `pnpm ds:sync-versions` в репозитории
дизайн-систем, а в продукте — повторный `prism-ds connect`.
