## Задача

Во время создания дизайн-системы выяснять, нужны ли продукту выразительные анимации,
сложные последовательности или 3D. После определения сценариев предлагать подходящие
библиотеки и фиксировать разрешение на их использование в конкретной системе.

Уникальные визуальные компоненты, например интерактивная 3D-клавиатура, должны иметь
понятное место создания, публикации, демонстрации и потребления. Обычный интерфейс
при этом должен сохранять переносимость и предсказуемый набор зависимостей.

## Архитектура

### Подтверждённые границы

- Объёмная, 3D-подобная или анимированная `Button` остаётся обычной `Button` общего
  контракта: тот же публичный импорт, существующая папка и совместимые props.
- Эффекты допустимы в любых компонентах текущего контракта. Их наличие не требует
  переноса компонента в специальную 3D-папку или создания другого источника токенов.
- Уникальный компонент определяется самостоятельным назначением и API. Он может
  быть обычным DOM-компонентом, анимационным паттерном или настоящей 3D-сценой.
- Motion и 3D подключаются по реальной потребности конкретной системы. Система без
  них использует обычный lifecycle и не приобретает дополнительные runtime-требования.
- Создание, изменение, использование, Showcase и CLI/TUI должны опираться на одни
  правила и один сгенерированный публичный каталог.

### Эффекты внутри обычного компонента и папка motion

3D-подобное оформление кнопки часто достигается CSS: гранями, тенями, перспективой
и изменением положения при нажатии. В этом случае Three.js не требуется. Настоящий
WebGL с геометрией, светом и камерой выбирается отдельно по сценарию.

Анимация и объём реализуются в существующих `src/components/button/Button.tsx` и
`button.css`, используют `tokens.source.json` и остаются внутренним поведением системы.
Не создаётся `Button3D`; API движка не передаётся в общий контракт. Например,
`variant="3d"` нельзя выдумать: текущий `ButtonVariant` имеет конкретный набор значений.
Если нужен выбор между плоским и объёмным режимом для каждого экземпляра и существующий
API его не выражает, это отдельное решение о совместимом API.

Опциональная внутренняя папка `src/motion/` хранит общие эффекты, хуки и orchestration
конкретной системы, когда несколько компонентов действительно ими пользуются. Она
не содержит второй набор токенов и не становится обязательной частью каждого пакета.
Публичный `/motion` появляется только при наличии самостоятельных экспортируемых
паттернов, например `Reveal`; внутренние helpers сами по себе публичного входа не требуют.

### Общий контракт и расширения конкретной системы

Существующая система продолжает реализовывать контракт версии 4. Её стандартные
компоненты сохраняют совместимый API, а визуальное движение определяется системой.
Пользователь `Button` или `Dialog` не должен знать, каким движком они реализованы.

Для уникальных визуальных компонентов используются отдельные публичные входы того же
пакета. Имя папки не определяет способ рендеринга. Реализованная структура входов
System B (обобщённый пример; `motion`-вход появится только при реальных паттернах):

```text
@prism-system/ui-northstar             стандартные компоненты
@prism-system/ui-northstar/tokens      существующий серверный вход с токенами
@prism-system/ui-northstar/motion      Reveal, StaggerGroup и подобные паттерны
@prism-system/ui-northstar/custom/keyboard-scene  уникальный KeyboardScene
@prism-system/ui-northstar/custom/workflow-map    уникальный DOM-компонент
```

Каждый расширенный компонент экспортируется из одного подходящего входа. Создаются
только входы с реальными реализациями; пустые модули заранее не генерируются.
Имена здесь иллюстрируют назначение, а не задают новый обязательный каталог.
Для уникальных компонентов можно использовать `src/custom/<kebab>/`; анимированная
кнопка из общего контракта остаётся в `src/components/button/`.

Расширения принадлежат своей дизайн-системе: используют её токены и визуальный язык,
имеют собственные типы props и версии API. Переключение систем гарантирует совместимость
общего контракта; наличие одинаковой 3D-сцены во всех системах не предполагается.
Расширения не добавляются в `DesignSystem.components` и не требуют второго runtime-реестра.

### Владение компонентами

| Сценарий | Владелец |
| --- | --- |
| Переходы, состояния и движение стандартных компонентов | Пакет дизайн-системы |
| Самостоятельный визуальный паттерн, который система обещает поддерживать и поставлять | Расширение той же системы |
| Размещение компонентов на странице, маршруты, загрузка данных, покупки и бизнес-процесс | Продуктовое приложение |
| Визуальная экспериментальная сцена без устойчивого API | Продуктовый прототип; перенос в библиотеку после определения границ |

Пример: `KeyboardScene` может отображать модель клавиатуры, подсвечивать выбранную
клавишу и передавать событие выбора. Приложение определяет цену, ассортимент, URL,
сохранение конфигурации и корзину. Источник модели и права на её распространение
определяются для конкретного сценария; приватный продуктовый asset не попадает в
публикуемый пакет автоматически.

Отдельная дизайн-система нужна при самостоятельном визуальном языке продукта.
Необычный компонент сам по себе не требует создания ещё одной системы.

### Выбор движка и установка

| Задача | Предпочтительный старт |
| --- | --- |
| Короткие hover/focus/state переходы | CSS и существующие motion-токены |
| React entrance/exit, layout и gesture-анимации | Motion |
| Управляемые timelines, сложные scroll/SVG последовательности | GSAP и его React-интеграция |
| Геометрия, материалы, освещение и камера | Three.js; React Three Fiber при необходимости React-сцен |

Выбор делается по реальным сценариям. Motion и GSAP могут сосуществовать при разных
задачах, но один элемент и его анимируемое свойство должны иметь одного владельца.
Универсальный слой, скрывающий все движки за одинаковым API, заранее не создаётся.

Разрешение на библиотеку фиксируется для конкретной системы и задачи. Точные версии,
peer ranges и фактические зависимости принадлежат `package.json` и lockfile. Интервью
фиксирует разрешение и причину выбора, а не дублирует версии пакетов.

Установка в монорепозитории и установка в продукте — разные действия. Разрешение
использовать GSAP при разработке системы не означает автоматическое изменение
зависимостей любого потребителя.

- Если основной вход действительно использует движок, он объявляется обычной runtime
  dependency системы. Такой движок необходим всем потребителям этого входа.
- Если движок нужен только расширению, предпочтительны optional peers и отдельный
  импорт. Потребитель выбранного расширения явно устанавливает совместимые peers.
- Optional peer не устанавливается автоматически и становится необходимым при
  использовании соответствующего расширения. Отсутствие peer у неиспользуемого
  расширения не должно считаться поломкой обычного интерфейса.
- Если нужна независимая установка и отдельный цикл выпуска большой группы сцен,
  её можно вынести в companion-пакет, например `@prism-system/experiences-northstar`.
  Такой пакет не регистрируется как ещё одна полная дизайн-система. Это следующий
  шаг при доказанной необходимости, а не обязательная структура первого этапа.

Отдельный вход решает границу импорта; optional peers или companion-пакет решают
границу установки. Эти свойства проверяются отдельно.

### Один источник каталога и явные метаданные

Существующие `exports` и `publicApi` описывают пути и публичные имена, но не сообщают,
имеет ли Button объём, использует ли сцена WebGL и какие peers нужны конкретному входу.
Поэтому для поставленной задачи нужен структурированный каталог, а не только список
дополнительных экспортов.

Единый источник — package-owned descriptor: стандартные компоненты сохраняют
свои записи и получают необязательные сведения об эффектах; самостоятельные компоненты
имеют отдельные декларации в той же системе. Генератор сопоставляет эти сведения с
реальными публичными экспортами, metadata пакета и примерами, затем формирует один
публичный манифест. Формат секций и полей реализован в schema 5; примеры ниже
иллюстрируют форму, а строгая схема — источник истины.

Сведения об эффектах необязательны для обычных систем. Отсутствующее поле означает,
что свойство не описано, и не даёт оснований придумывать анимацию или способ рендеринга.
Новые внутренние папки и зависимости не создаются при отсутствии соответствующих задач.

| Сведение | Назначение и источник |
| --- | --- |
| Имя и принадлежность общему контракту либо custom API | Канонические core-имена и декларация уникального компонента |
| Описание, variants, части, docs и пример | Реализованный API и descriptor |
| Эффекты: глубина, движение, настоящая 3D-сцена | Явная декларация реализации, без угадывания по названию |
| Рендеринг: DOM/CSS, WebGL либо сочетание | Явная декларация; объёмное CSS-оформление не объявляется WebGL |
| Публичный импорт | Проверенный путь из `package.json.exports` и фактический экспорт |
| Требования зависимостей для выбранного входа | Ссылка декларации на dependency/peer; диапазон берётся из `package.json` |
| Fallback и reduced-motion поведение | Документированное и проверенное поведение компонента |

Наличие ключа в `components` остаётся единственным источником доступности общего
контракта. Для уникальных компонентов источник — наличие их проверенной декларации
в новом каталоге. В `capabilities.categories` новые motion/3D/custom-категории не
добавляются: эффекты служат фильтрами представления, а не вторым списком доступности.
Отдельный runtime-реестр и новый обязательный каталог core-компонентов не создаются.

Новые секции реализованы: package-owned descriptor — `schemaVersion: 4`, shipped
`design-system.json` — `schemaVersion: 5`. Source/schema, генератор, maintainer checks,
consumer validators, diff, CLI/TUI и app-синхронизация обновлены согласованно.
Нельзя добавить неизвестные поля в текущую schema 5 и считать старый `prism-ds`
совместимым. Остаётся одна текущая форма манифеста; миграция формата не создаёт ещё
одного контракта компонентов и сама по себе не меняет `contractVersion: 4`.

### Showcase

Showcase получает метаданные из сгенерированного публичного манифеста выбранной системы.
Обычная Button остаётся в обычном каталоге и показывает своё реальное оформление,
эффекты и состояния. Уникальные компоненты показываются в том же каталоге отдельной
группой только у систем, которые их действительно поставляют. Можно фильтровать по
движению, глубине и способу рендеринга независимо от принадлежности общему контракту.

Для каждого уникального API нужен явный демонстрационный сценарий с корректными props.
Одних меток `3d` или `motion` недостаточно, чтобы автоматически построить пример.
Синхронизация приложений генерирует загрузчики объявленных публичных модулей рядом с
существующей регистрацией системы; core-реестр остаётся один. Showcase компонует примеры
и задаёт демонстрационные данные, а оформление и эффекты остаются в пакете.

Тяжёлые сцены загружаются при открытии выбранного примера. Для них показываются загрузка,
ошибка/fallback, mobile и reduced-motion сценарии; невидимая сцена останавливается или
размонтируется. Страница обычных компонентов не загружает все сцены ради карточек каталога.
Reference App сохраняет роль фиксированного теста совместимости общего контракта.

### CLI/TUI как точка входа потребителя

`prism-ds components` строит один каталог из манифеста точной установленной
версии: общий контракт, реализованные дополнительные контракты и уникальные компоненты.
CLI и вкладка Components в TUI используют один результат, без отдельных ручных списков.
При отсутствии уникальных компонентов их группа скрывается, обычная работа сохраняется.

Пример формы вывода (фактический CLI печатает сгруппированные строки с `api vN`,
import-путём и requirements):

```text
Button
  общий обязательный компонент; DOM/CSS; глубина и анимация нажатия
  импорт: @prism-system/ui-northstar

KeyboardScene
  уникальный компонент; WebGL; 3D и анимация
  импорт: @prism-system/ui-northstar/custom/keyboard-scene
  дополнительные peers: three, @react-three/fiber

InteractiveWorkflowMap
  уникальный компонент; DOM; анимация переходов
  импорт: @prism-system/ui-northstar/custom/workflow-map
```

Карточка выбранного компонента объясняет доступность, импорт, API, эффекты, требования,
fallback и ссылку на пример. `components <name>` разрешает имя по фактическому каталогу,
а не предполагает, что любой новый компонент обязан быть canonical. `info` показывает
состав выбранного опубликованного релиза; upgrade diff включает изменения custom API
и peer-требований. Метаданные эффектов не подтверждают визуальное совпадение сами по себе.

`check`/`doctor` проверяют prerequisites используемого входа. Отсутствие peers для
неиспользуемой сцены не ломает обычную систему. Каталог и диагностика читают публичные
данные, не выполняют код пакета и не устанавливают движки. Установка, если нужна,
остаётся внутри `install`/`use`/`upgrade` с явным выбором и dry-run планом.

## Изменение интервью

На стадии направления и ограничений уточнять назначение движения: реакция на действие,
переход между состояниями, повествование при прокрутке или интерактивная сцена.
Выяснять потребность в 3D отдельно от интенсивности обычных UI-анимаций.

Если решение ещё не принято, агент прямо спрашивает о кнопках: плоское оформление,
тактильная глубина при нажатии или выраженные анимационные эффекты. Это вопрос о
существующей Button. Самостоятельные сцены и другие уникальные компоненты обсуждаются
отдельно по продуктовым сценариям; установка Three.js не следует из слова «объёмный».

Затем предложить технический набор с причиной и ценой выбора: зависимости, поддерживаемые
React-версии, ожидаемая загрузка и сложность сопровождения. Пользователь может выбрать
или делегировать решение. При делегировании агент фиксирует собственную рекомендацию
как делегированную, а не приписывает пользователю конкретный выбор.

В brief сохранить `foundations.motionIntensity`, записывать эффекты существующих
компонентов в `componentTreatments`, общие сценарии в `motionScenarios`, самостоятельные
запросы в `requestedCustomComponents`, значимые решения о библиотеках в `decisionNotes`.
Новые необязательные поля описаны в authoring-схеме; генератор пока сохраняет их как
дополнительный контекст и не превращает в компоненты, метаданные или установку пакетов.
Старый brief без этих полей не включает новые зависимости. Brief публикуется, поэтому
хранит только безопасные продуктовые и визуальные решения.

## Критерии готовности

Статус: автоматические проверки для каталога, расширений и упакованных артефактов
пройдены; браузерные пункты (WebGL canvas, fallback, reduced motion, эмуляция ширин
375/768/1440) подтверждены на production-сборке Showcase при эмуляции DPR1. Визуальный
baseline, физическое устройство/GPU и axe/screenreader не проверялись; остановка
невидимой сцены и потеря контекста остаются неподтверждёнными. Прогоны подтверждают
выполненные проверки, а не обязательно статус release-ready; подробности — в разделе о
проверках выше.

- Стандартный Button с эффектами использует прежний API и папку; остальные системы
  и обычные компоненты не требуют новых файлов, настроек или движков.
- Основной импорт не требует optional peers уникальных компонентов и не импортирует
  их реализации. Его declarations также не требуют типов неиспользуемого движка.
  Движок, необходимый стандартным компонентам конкретной системы, объявляется её
  настоящей runtime dependency; его стоимость измеряется, а не объявляется нулевой.
- Токены остаются серверно безопасным входом. Motion/3D модули имеют корректную
  клиентскую границу, не обращаются к браузерному API при серверном импорте и
  корректно очищают timelines, события и графические ресурсы.
- Набор экспортов, декларации, манифест и содержимое tarball согласованы. Отсутствующий
  экспорт не показывается как доступный компонент.
- CLI/TUI и Showcase получают одинаковый каталог с типом API, эффектами, рендерингом,
  зависимостями и проверенными примерами. У обычной системы нет пустых обязательных
  custom-секций; отсутствующие metadata не превращаются в придуманные возможности.
- Поддерживаемые сочетания React и графических зависимостей проверены на потребителях.
  Широкий peer range сам по себе не считается подтверждением совместимости.
- Reduced motion, доступность управления, loading/error/fallback, мобильный сценарий
  и остановка невидимой сцены проверены в браузере. Контент и действия доступны
  при отключённой анимации или недоступном графическом рендеринге.
- Отдельно измерены загрузка обычного интерфейса и страницы со сценой, стоимость
  модели/текстур и рендеринга. Конкретный бюджет определяется продуктовым сценарием.
- Strict usage не ослабляется глобальным ignore. Допустимое оформление нового паттерна
  живёт в пакетной реализации; границы статического анализа документированы.

Полный прогон и browser QA выполнены; опциональные следующие шаги (baseline, физическое
устройство/GPU, axe/screenreader, остановка невидимой сцены и потеря контекста)
перечислены в разделе «Откуда продолжать».
Общие runtime-провайдеры, универсальный animation adapter, новый реестр и отдельные
пакеты вводятся только при конкретной потребности, которую нельзя ясно решить
существующими границами.
