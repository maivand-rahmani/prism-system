# Create a Design System

Use this skill when asked to create a new design system in this repository. The result
is a package for the current contract (version 4) generated by the repository tooling,
then refined inside that package. The generator creates current-contract packages; do
not scaffold retired contract versions or invent another package workflow.

For component names, contracts, and capability rules, use the canonical sources linked
in [lifecycle guidance](../references/lifecycle.md). Do not copy a component catalog
into this skill. In particular, `@prism-system/ui-core` and its schemas own the
required/optional contract; do not restate or fork that catalog here.

## Interview and approval

Gather enough information to make concrete system-wide visual decisions. Ask about the
product and audience, desktop/mobile/responsive targets, interface type and data density,
visual direction and references, foundations, and the complete page/form scenarios the
system must support. Include responsive behavior, typography hierarchy, and loading,
error, and empty states. Separate three things in the brief:

- **Requested capabilities:** which optional core contracts seem useful. This is a
  request for the implementation, not proof that a capability exists.
- **Actual capabilities:** determined only by the package runtime map, descriptor, and
  published manifest after implementation. Do not record intended capabilities as actual
  ones.
- **Product compositions:** pages, forms, workflows, and domain-specific patterns that
  the product will compose from primitives. These are not automatically reusable
  components.

Present the resulting brief and get user confirmation before generating or implementing
when material visual decisions are still unresolved. Preserve decisions and explicit
brief approval already given in the active session; do not ask for ritual reconfirmation.
Ask only when a material decision is missing or has changed. Once approval exists,
continue with generation.

## Brief and generation

Write the approved brief to `design-briefs/<id>.json` using
[`design-brief.schema.json`](./design-brief.schema.json). Existing briefs remain valid:
new scenario and capability-intent fields are optional. Keep the existing `components`
field readable for older briefs; interpret it as mixed notes that must be classified,
not as a list of components to generate.

After approval, preview and generate with `pnpm ds:create <id> --name "<Display Name>"
--brief design-briefs/<id>.json --dry-run`, then run the same command without
`--dry-run`. The command creates the contract-version-4 baseline and registers it. Do not
hand-create the baseline or edit generated contract catalogs. Implement only within
`packages/<id>`.

The package's `tokens.source.json` is the sole editable token source. Refine it to
match the approved visual foundations; generated TypeScript tokens, CSS variables,
Tailwind bridge, and manifest are outputs. Declare real variants, examples, compound
members, documentation paths, and actual optional implementations in the package
descriptor (`design-system.source.json`). The descriptor stays `schemaVersion: 3` and
never declares `capabilities`; the generated `design-system.json` is `schemaVersion: 4`
and carries the canonical `capabilities.categories` inventory, while actual support
remains the descriptor/runtime component set. `package.json` exports and public
entrypoints own public artifact and CSS paths; the descriptor does not. An optional
capability counts only when its implementation, runtime component map, public export,
styles import, and descriptor agree. Never create empty stubs. Use
`pnpm ds:manifest <id> --write` to regenerate generated token artifacts and manifest
after source changes; never hand-edit generated files or add a `capabilities` block to
the descriptor.

Compare `source.design` with the neutral scaffold and the approved brief. Replace generic
scaffold choices with the brief's decisions before polishing component styling. Keep
visual language in the system package; keep Showcase and Reference App as composition
surfaces without overrides.

## Review and finish

Review the whole page and form scenarios, not just isolated controls. Include narrow and
wide layouts, typography hierarchy, loading/error/empty states, focus and keyboard
behavior, and any implemented optional capability. Product-specific compositions may be
demonstrated in apps, but do not turn a one-product workflow into a system contract
without evidence it is a reusable visual pattern.

Run `pnpm ds:check <id>` once after implementation and visual review. It runs package
build/typecheck/lint as part of its validation; do not repeat those commands unless the
check was explicitly run with `--no-commands` or a later edit invalidated the result.
Run `pnpm ds:sync-versions <id> --check` when the work changes version alignment or
release metadata. Report commands and visual reviews accurately. Versioning, release
preparation, and publishing are separate explicit steps; do not infer them from package
creation.
