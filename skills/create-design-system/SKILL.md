# Skill: Create a Design System

Agent-neutral instructions for creating a new design system in the `prism-system`
monorepo. Any compatible external coding agent can follow this document. It uses only
Markdown, repository files, and repository scripts — no model APIs, SDKs, MCP servers,
hosted agents, or agent-specific tool syntax.

## When to use this skill

Use this skill when a user asks to create a new design system, for example:

> Create a design system for Pulse.

The outcome is a new `packages/<id>` design-system package generated by deterministic
repository tooling, with the visual language implemented inside that package.

**V2 creates packages, not an AI runtime.** This repository contains no LLM integration
or built-in agent. The user runs their own coding agent; this skill is the process that
agent follows.

## Repository architecture

```text
apps/*  ──────────────►  @prism-system/ui-system-*  ──────────────►  @prism-system/ui-core
```

- `@prism-system/ui-core` is the **unstyled** foundation. It owns contracts, shared
  types, utilities, accessibility helpers, and unstyled primitives. It must never
  contain colors, tokens, typography, spacing, radius, shadows, motion, or component
  appearance.
- Each `@prism-system/ui-system-*` package owns its **entire visual language**: tokens,
  styles, variants, states, and concrete component implementations. It consumes core and
  nothing from another system.
- `apps/showcase` and `apps/reference-app` only compose. They own layout, placement,
  and reference scenarios, never visual overrides.

## Non-negotiable boundaries

1. **Core stays unstyled.** Never add visual decisions to `@prism-system/ui-core`.
2. **Systems own the visual language.** Keep every color, token, style, variant, state,
   and motion value inside the generated package (`src/tokens`, `src/styles`,
   `src/components`).
3. **Apps compose only.** Never edit Showcase or Reference App to add visual overrides,
   restyle a system, or work around a package gap.
4. **No cross-system imports.** A design system never imports another design system.
   Cross-package imports use `@prism-system/*` package names, never relative paths that
   cross a package boundary.
5. **Fourteen immutable required V2 components**, in canonical order:

   `Button`, `Input`, `Textarea`, `Card`, `Badge`, `Checkbox`, `RadioGroup`, `Switch`,
   `Select`, `Tabs`, `Dialog`, `DropdownMenu`, `Tooltip`, `Separator`.

   These required exports are fixed: never rename, remove, or alter one. Optional
   product-specific components are allowed as **additions** and must not reduce,
   substitute, or otherwise change the required set.

6. **Optional additions are package-local.** Add extra components only inside the
   generated package (`packages/<id>`), for example as a separate module under
   `src/components`. They may be exported through an additive package-owned export, but
   the required exports and the shared contract must stay intact. Never introduce a
   component by changing a required export.

7. **Use the generator for the baseline.** Do not hand-create the package structure or
   hand-edit the generated baseline files (including the required exports) to create the
   package — `pnpm ds:create` owns that. After generation, package-local visual
   implementation and additive extensions are allowed only inside `packages/<id>`.

## Workflow

Follow these steps in order. Do not skip the interview or the confirmation step.

### Step 1 — Confirm the target id

Choose a lower-kebab-case id matching `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$`, for example
`pulse` or `fancy-tech`. Reserved ids that cannot be used: `core`, `showcase`,
`reference-app`.

The id determines `packages/<id>`, the package name `@prism-system/ui-<id>`, the tokens
export, and the CSS class prefix. Confirm the id with the user before generating.

### Step 2 — Run the Design Interview

Ask only what is needed to make concrete visual decisions. Group related questions, use
the user's vocabulary, and ask practical follow-ups instead of dozens of filler
questions. Cover four areas.

**Product**

- What is the product?
- Who is it for?
- Which platform(s): desktop, mobile, or responsive web?
- What kind of interface is it (dashboard, editor, console, settings surface, ...)?
- How data-heavy is it?

**Visual Direction**

- How should the product feel?
- Compact or spacious?
- Calm or expressive?
- Technical or friendly?
- Light-first or dark-first?
- Which existing products does the user like visually?
- What should be avoided?

**Foundations**

- Accent direction
- Color temperature
- Contrast
- Typography character
- Dominant radius
- Surface model
- Borders
- Elevation
- Motion intensity

**Components**

- Which of the fourteen required components are most important?
- Are there product-specific components?
- Is high control density needed?
- What complex composition scenarios are expected?

### Step 3 — Present the Design Brief and get explicit confirmation

Present a compact, human-readable brief (project, product, direction, references,
foundations, components, avoid). Make the choices concrete enough to review.

Then **stop and ask the user to confirm or correct the brief.** Do not generate the
package or implement any component before the user confirms. If they change a decision,
update the brief and confirm again.

### Step 4 — Write the Design Brief

Write the confirmed brief to `design-briefs/<id>.json`. It must validate against
[`design-brief.schema.json`](./design-brief.schema.json) and include these fields:

| Field           | Type     | Purpose                                                 |
| --------------- | -------- | ------------------------------------------------------- |
| `project`       | string   | Product/project name; used as the default display name. |
| `product`       | string   | One-sentence description of the product.                |
| `audience`      | string   | Primary users and context.                              |
| `platform`      | string   | Desktop, mobile, responsive web, ...                    |
| `interfaceType` | string   | Kind of interface.                                      |
| `dataDensity`   | string   | How information-dense the UI is.                        |
| `direction`     | string[] | Feel adjectives (compact, technical, dark-first, ...).  |
| `references`    | string[] | Products the user likes visually.                       |
| `foundations`   | object   | The nine foundation fields below.                       |
| `components`    | string[] | Product-specific components and composition scenarios.  |
| `avoid`         | string[] | Visual decisions to avoid.                              |

`foundations` requires these string fields: `accentDirection`, `colorTemperature`,
`contrast`, `typographyCharacter`, `dominantRadius`, `surfaceModel`, `borders`,
`elevation`, `motionIntensity`.

Extra fields are allowed at the root and inside `foundations` so the interview can record
additional decisions without breaking the schema. Keep arrays as arrays of strings; the
generator trims and drops empty entries.

Minimal shape:

```json
{
  "project": "Pulse",
  "product": "Developer productivity application for inspecting CI pipelines",
  "audience": "Professional developers working long sessions on desktop",
  "platform": "responsive web",
  "interfaceType": "data console",
  "dataDensity": "high",
  "direction": ["compact", "technical", "dark-first", "restrained"],
  "references": ["Linear", "Raycast"],
  "foundations": {
    "accentDirection": "cool blue",
    "colorTemperature": "cool",
    "contrast": "low-contrast surfaces, strong text",
    "typographyCharacter": "neutral grotesk with strong hierarchy and dense body text",
    "dominantRadius": "compact (4-6px)",
    "surfaceModel": "flat surfaces with subtle elevation",
    "borders": "visible 1px hairlines",
    "elevation": "subtle elevation, no heavy shadows",
    "motionIntensity": "minimal 120-180ms transitions"
  },
  "components": ["CommandBar", "MetricCard", "dense data table toolbar"],
  "avoid": ["oversized cards", "heavy gradients", "pill-heavy UI"]
}
```

### Step 5 — Generate the package deterministically

Preview, then generate:

```bash
pnpm ds:create <id> --name "<Display Name>" --brief design-briefs/<id>.json --dry-run
pnpm ds:create <id> --name "<Display Name>" --brief design-briefs/<id>.json
```

`pnpm ds:create` is the only correct way to create the package. It validates the id,
renders `templates/design-system` into `packages/<id>`, writes `README.md`, `AGENTS.md`,
`LICENSE`, and `package.json`, creates `src/tokens`, `src/styles`, and all fourteen
components, writes the normalized `design-brief.json`, and registers the system in
`config/design-systems.json` with `contract: "v2"`.

It fails if `packages/<id>` already exists, and it rolls back the generated package if
registration fails. Do not hand-create these baseline files or hand-edit the generated
required exports to create the package — use the generator for the baseline. If
registration metadata needs refreshing, re-run `pnpm ds:register <id>` — never hand-edit
the manifest. Once generation succeeds, package-local visual implementation and additive
extensions inside `packages/<id>` are expected (see Step 6).

### Step 6 — Implement the visual language (package only)

1. Read `packages/<id>/AGENTS.md` and `packages/<id>/README.md` first; they carry the
   generated visual direction and avoid list.
2. Implement foundations in `src/tokens` and `src/styles`, then refine the fourteen
   components in `src/components`.
3. Use `@prism-system/ui-core` contracts, primitives, `cn`, and `cva` before writing a
   new primitive.
4. Keep the package-owned tokens, CSS class prefix, variants, and states inside the
   package.
5. Preserve compound static members such as `Card.Header`, `Tabs.List`, `Dialog.Content`,
   and `DropdownMenu.Item`.
6. Edit only files inside `packages/<id>`. Never edit `core`, another system, an app, a
   script, or a template to make the new system look right.
7. Optional additions stay additive: add product-specific components as separate
   package-local modules under `src/components` and export them additively (from the
   package root or a package-owned module). Never rename, remove, or alter a required
   export, and never make an addition a requirement of the contract.

### Step 7 — Human review loop

The intended review surfaces are Showcase and Reference App, where the user judges the
system in isolation and in composition. Automatic registration of new systems into those
apps is a later phase and may not be available yet. If the new system does not appear in
an app, report that integration gap; do not edit app code by hand to compensate.

Apply all visual feedback to `packages/<id>` only, then re-review. A system that only
looks correct in Showcase but breaks in composition is not finished.

### Step 8 — Validation handoff (current and intended)

Run the generated package's own checks now:

```bash
pnpm --filter @prism-system/ui-<id> build
pnpm --filter @prism-system/ui-<id> typecheck
pnpm --filter @prism-system/ui-<id> lint
```

`pnpm ds:check <id>` is the intended full validation command (package structure,
naming, exports, required components, tokens, registration, README/AGENTS). It is **not
implemented yet** — do not invent it or hand-replace it. Once it exists, run it and
require it to pass.

Do not claim the system is complete while required checks are unavailable. State exactly
which checks ran and which are still pending. `pnpm ds:release <id>` is the intended
future release handoff; it does not exist yet. Never publish, version, or run a release
for a new system before human approval and full validation.

## Stop / finish checklist

- [ ] Id is lower-kebab-case and not reserved.
- [ ] Design Interview covered product, visual direction, foundations, and components.
- [ ] User explicitly confirmed the compact Design Brief.
- [ ] `design-briefs/<id>.json` is valid against `design-brief.schema.json`.
- [ ] `pnpm ds:create` generated `packages/<id>` and registered it in
      `config/design-systems.json` as `contract: "v2"`.
- [ ] The fourteen required components are present and unrenamed.
- [ ] Optional additions, if any, are package-local and additive (no required export was
      changed).
- [ ] Visual foundations and component refinements live only in `packages/<id>`.
- [ ] The system was reviewed in Showcase and Reference App (or the integration gap was
      reported).
- [ ] Generated package build, typecheck, and lint were run and reported honestly.
- [ ] `pnpm ds:check <id>` was run if available, or its unavailability was disclosed.
- [ ] Nothing was published or versioned.

## Common failure modes

- **Implementing before confirmation.** Never generate or style a component before the
  user approves the Design Brief.
- **Hand-creating the package.** Do not copy template files by hand or hand-edit the
  generated baseline or required exports to create the package; always go through
  `pnpm ds:create`. Package-local implementation and optional additions come only after
  generation, inside `packages/<id>`.
- **Altering the required contract.** Optional product-specific additions are welcome, but
  never rename, remove, or change one of the fourteen required exports to make room for
  them.
- **Leaking visuals into core or apps.** Colors, tokens, radius, shadows, and motion
  belong in the system package; apps compose and never override.
- **Cross-system imports.** A system must not depend on another system.
- **Breaking the contract.** Do not rename, remove, or reduce the fourteen required
  components.
- **Editing apps to compensate.** If Reference App or Showcase needs overrides, the
  system is incomplete — fix the package, not the app.
- **Over-claiming completion.** Do not report success for `ds:check`, app integration, or
  release until those tools actually exist and ran.
