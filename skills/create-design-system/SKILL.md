# Create a Design System

Use this skill when the user asks to create a design system in this repository, from a
vague request such as "we need a design system", "brand this product UI", or "make it look
like Linear", through to an already-approved brief. The result is a package for the current
contract (version 4) generated by the repository tooling, then refined inside that package.
You act as an experienced design-system professional: understand the product's real intent,
resolve the material visual decisions with the user, and translate the outcome into one
coherent reusable visual system. This is not a questionnaire to fill in, and it is not
product application work; product screens, data, and behavior stay in the product.

Before asking anything, read the current session, the user's existing decisions, and any
brand assets, screenshots, or reference links already provided. Do not ask answered
questions or repeat an interview that already happened, respect the repository, and never
overwrite or revert the user's uncommitted changes. This document is English guidance for
you; the questions, options, and summaries you present follow the user's language.

Handoffs: this skill owns creating a new system. Evolving an existing package belongs to
[`modify-design-system`](../modify-design-system/SKILL.md); building product screens from
an installed package belongs to [`use-design-system`](../use-design-system/SKILL.md).

For component names, contracts, and capability rules, use the canonical sources linked in
[lifecycle guidance](../references/lifecycle.md). Do not copy a component catalog into this
skill. In particular, `@prism-system/ui-core` and its schemas own the required/optional
contract; do not restate or fork that catalog here.

## Interview in adaptive phases

Work through these phases in order, skipping any phase the session already answers:

1. **Product and context** — what the product is, who uses it and in which conditions, the
   target platform and interface type, and one to three real screens or forms the system
   must support. Prefer open questions here: only the user knows the real product.
2. **Direction and references** — the intended feel, brand assets, and interfaces the user
   likes. When the user says "like Linear", interpret which traits matter (density,
   restraint, hierarchy, motion) and which traits must not be copied; ask a choice question
   when the intended trait is ambiguous. A product name is not a decision.
3. **Constraints and hierarchy** — themes (light/dark), density, content hierarchy,
   localization or platform constraints, accessibility expectations, and what to avoid. Do
   not collect exact token values, hex codes, or component API details; those are
   implementation, not intent.
4. **Foundations proposal** — for still-unresolved decisions, propose one small coherent
   bundle (for example one accent with its temperature, contrast, and radius) that fits the
   confirmed direction, instead of walking through every schema key. Let the user accept,
   adjust, or delegate.
5. **Summary and readiness** — present a concise summary of product, scenarios, direction,
   constraints, foundations, and requested capabilities; confirm it, or continue directly
   when the user already approved or delegated those decisions.
6. **Generation and implementation** — once ready, follow the sections below.

Ask one meaningful question per turn, or at most two when they are tightly coupled; never
dump a multi-question form. When the environment provides a structured question capability,
use it with 3-5 grounded, mutually distinctive options that each carry practical meaning,
plus the user's own answer where the environment supports one; otherwise present the same
options concisely as text. Ground the options in the confirmed direction, and use open
questions for real product details. If the user delegates a choice, make a recommendation
with its tradeoff and record it as delegated; do not pretend the user chose it. See
[design-interview.md](../references/design-interview.md) for an optional question bank and
branching walkthrough examples.

Do not ask about technical contract, export, tooling, or repository mechanics you can
inspect yourself, and do not ask whether basic accessibility should be provided: focus,
keyboard, contrast, and reduced-motion behavior are always in scope, constrained by the
confirmed intent rather than treated as optional features. Do not guess critical decisions
from the product name or from a reference.

## Readiness to generate

A brief is generator-ready when it has the product and audience, at least one real screen or
form scenario, a direction with the traits to pursue and avoid, constraints, and foundations
that are approved or explicitly delegated. No material decision may remain proposed and no
material conflict may remain unresolved. Keep these three classifications separate:

- **Requested capabilities** — which optional core contracts seem useful. This is intent
  for the implementation, not proof that a capability exists.
- **Actual capabilities** — determined only by the package runtime map, descriptor, and
  generated manifest after implementation. Do not record intended capabilities as actual
  ones.
- **Product compositions** — pages, forms, workflows, and domain-specific patterns the
  product will compose from primitives. These are not automatically reusable components.

If a material decision is still missing, ask one targeted question and resolve it; do not run
an infinite interview. If an approved brief or explicit delegation already covers the
decisions, proceed without forced reconfirmation. Draft notes may be incomplete while the
interview is in progress, but never fill required brief fields with "TBD" or placeholders
just to satisfy the schema or generation. A generator-ready brief contains concrete
approved or delegated decisions.

## Brief and generation

Write the approved brief to `design-briefs/<id>.json` using
[`design-brief.schema.json`](./design-brief.schema.json). The schema is the authoring
contract; `pnpm ds:create --brief` normalizes only the fields it uses (`project`, `product`,
`direction`, `references`, `foundations`, `components`, `avoid`), preserves unknown extra
fields, and performs no full schema validation. The brief is copied into the package as
`design-brief.json` and ships in its tarball, so write only sanitized product and visual
intent: no secrets, customer-sensitive data, private reference URLs, personal details, or
interview transcripts. Keep the existing `components` field readable for older briefs and
interpret it as mixed notes that must be classified, not as a list of components to
generate.

Record significant choices with the optional `decisionNotes` (`confirmed`, `delegated`,
`proposed`), reference traits with `referenceNotes`, and remaining questions with
`openQuestions`. Do not duplicate a value another field already owns; a note carries the
decision and its rationale. A generator-ready brief has no material `proposed` decision.

After approval, preview and generate with `pnpm ds:create <id> --name "<Display Name>"
--brief design-briefs/<id>.json --dry-run`, then run the same command without `--dry-run`.
The command creates the contract-version-4 baseline, registers it, updates the repository
registry, and syncs the Showcase and Reference App integration files deterministically; do
not hand-create the baseline or hand-edit registry or app wiring. Implement only within
`packages/<id>`; apps compose the system for review and must not restyle or override package
internals.

## Implement the approved design

The generated package is a neutral scaffold, not the approved visual design.
`tokens.source.json` is the sole editable token source; refine it and `source.design` to
match the approved brief. Generated TypeScript tokens, CSS variables, Tailwind bridge, and
manifest are outputs. The brief's foundations and data density are not transformed into
tokens or `source.design` automatically; reconcile them manually. Declare real variants,
examples, compound members, documentation paths, and actual optional implementations in the
package descriptor (`design-system.source.json`). The descriptor stays `schemaVersion: 3`,
never declares `capabilities`, and never declares public artifact or CSS paths (those belong
to `package.json` exports and public entrypoints). The generated `design-system.json` is
`schemaVersion: 4` and carries the canonical `capabilities.categories` inventory; actual
support remains the descriptor/runtime component set, and availability is only the presence
of a key in the manifest `components` map.

The required contract is implemented in full even when the requested scenarios are narrow:
all twenty-nine required components ship. An optional capability counts only when its
implementation, runtime component map, public export, styles/CSS entry, descriptor, and
generated manifest agree; never create empty stubs. Regenerate generated token artifacts and
the manifest only with `pnpm ds:manifest <id> --write`; never hand-edit generated files or
add a `capabilities` block to the descriptor.

## Review and finish

Review the real screens and forms from the brief, not just isolated controls: narrow and
wide layouts, typography hierarchy, loading/error/empty states, focus and keyboard behavior,
contrast, reduced motion, and every implemented optional capability. Report requested
optional capabilities that were not implemented instead of implying they exist. Product
compositions may be demonstrated in apps, but do not turn a one-product workflow into a
system contract without evidence it is a reusable visual pattern.

Run `pnpm ds:check <id>` once after implementation and visual review. It runs package
build/typecheck/lint and the app integration commands as part of its validation; do not
repeat those commands unless the check was explicitly run with `--no-commands` or a later
edit invalidated the result. A passing automated check is not evidence that the visual
system suits the product; that judgment stays with the reviewed screens. Run
`pnpm ds:sync-versions <id> --check` when the work changes version alignment or release
metadata. Report commands and visual reviews accurately. Versioning, release preparation,
and publishing are separate explicit steps; do not infer them from package creation.
